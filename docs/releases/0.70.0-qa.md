## 일반 재생 · 녹화 꺼짐

`qa/measure-canvas-playback.py`는 재생이 시작된 뒤 두 MCP snapshot의 `frameCount` 차이를 벽시계 간격으로 나눈다. build170의 구간은 재생14.38–29.78초, build171은10.26–25.60초였다. 둘 다 첫 섹션 내다.

| 항목 | build170 | build171 초기 후보 | build172 이전 후보 |
|---|---:|---:|---:|
| 구간 길이 | 15.385초 | 15.356초 | 15.364초 |
| 시각 업데이트 콜백 | 235 / 15.27Hz | 854 / 55.61Hz | **873 / 56.82Hz** |
| 화면 `draw` 콜백 | 계측 없음 | 833 / 54.25Hz | **865 / 56.30Hz** |
| `draw` 비용 p50 / p95 / p99 | 계측 없음 | 8.48 / 10.46 / 10.93ms | 8.59 / 10.62 / 11.15ms |
| `updatePlaybackFrame` 비용 p50 / p95 / p99 | 계측 없음 | 0.87 / 0.98 / 1.03ms | 0.87 / 1.00 / 1.06ms |

build172 구간은 재생16.34–31.70초이며 역시 첫 섹션 안이다. 비용 백분위수는 **최근600 콜백** 버퍼이므로 위 15초 구간의 정확한 통계로 읽으면 안 된다. 최대 호출 간격은 앱 실행 전체의 누적값이고 비활성 시간도 포함한다. `frameCount`는 화면 표시 프레임 수가 아니라 시각 업데이트 타이머 횟수다. 실제 compositor FPS는 미측정이다. build170의 10초 `sample`에서 주 스레드 `AlbumCanvasView.draw → drawReadableLabels → isVisible → labelContext → HierarchyScene.contextBounds` 반복이 확인되었고, 이것이 이번 캐시 변경의 근거다. 이 수치만으로 실제 FPS가3.72배 올랐다고 주장하지 않는다.

독립 코드 리뷰는 캐시 경로의 동작 회귀를 찾지 못했지만, 별도 QA 리뷰에서 **선택된 포트가 라벨 배치 전에 핸들을 캐시하는 경우**를 발견했다. build171은 이 시나리오에서 새 라벨과 포트 겹침을 허용할 수 있다. 포트 캐시를 라벨 배치 직후 비우는 수정은 build172에 적용했다. 독립 재검토에서 캐시 무효화 순서를 확인했고, 실제 UI에서 포트를 선택한 화면을 육안 확인했다. 장시간·여러 라벨 배치는 추가 검증한다.

## 초기 녹화 동시 실행 · 실패

build171에서 같은 캔버스로 내장 곡을 녹화했다. 10.232초 구간(재생75.02–85.31초, 섹션 전환 포함)의 콜백은 시각 업데이트346 / 33.81Hz, 화면 `draw`269 / 26.29Hz, 영상 `draw`320 / 31.27Hz였다. UI의 최종 결과는173.49초 MP4, 2995프레임, 누락221프레임이다.

당시 PTS 전용 `qa/inspect-movie-timing.swift`가 AVAssetReader의 H.264 sample PTS를 표시 순서로 정렬해 검사한 값: 영상 sample2999개, 평균17.32fps, PTS 간격 p50 63.33ms / p95 85ms / p99 95ms, 66.67ms 초과 간격512개, 최대 간격320ms. 오디오 첫 PTS0초, 첫 영상 PTS0.363초다. `videoDuplicatePTS=1`은 **동일 타임스탬프**만 뜻하며 당시에는 영상 내용 중복을 검사하지 않았다. UI의2995와 파일2999 sample 차이도 조사 대상이다. MP4의 실제 플레이어 시청·청취 및 AV offset 정밀 검증은 미수행이다. 이 결과는 녹화 gate FAIL이다.

## 녹화 경로 수정 후 build179 · 부분 통과

build173에서 캡처·인코딩 비용을 분리했으며 AppKit의 같은 캔버스 2회 그리기를 확인했다. build174의 직접 그리기는 영상이 상하 반전되었고 build175는 글자만 뒤집혔다. flipped CoreGraphics CTM과 `NSGraphicsContext`를 함께 설정한 build176에서 앱/파일 양쪽의 방향과 한글이 정상으로 돌아왔다. build177은 녹화 중 화면에 마지막 캡처 이미지를 재사용했다. build178 이후에는 프로파일에서 가장 비싼 라벨 측정의 캐시를 넣었고, 독립 리뷰가 찾아낸 창 폭별 캐시 증가를 build179에서 유효 폭 정규화·512항목 상한으로 고쳤다. 편집기 등 visible subview가 있으면 기존 AppKit 캡처 경로를 유지하지만 그 경로의 실제 GUI 검증은 남아 있다.

build179에서 세로 창·1080×1206pt 캔버스·첫 섹션 `section/fit/subtle` 팔로우를 사용했다. 녹화 없는 15.324초 구간은 시각 업데이트880회/**57.43Hz**, 화면 `draw`876회/**57.17Hz**였다. 이 역시 실제 compositor 표시 FPS가 아니라 콜백이다. 녹화 중 15.361초 MCP 계측 구간은 캡처450회/**29.29Hz**, 캡처 비용 최근600회 p50/p95/p99 **10.54/12.79/13.63ms**, 인코더 drop0이었다. 캡처 미리보기 재사용으로 화면 `draw` 비용 최근600회 p50 **0.026ms**였다. 화면 `draw` 호출 수는 고유 표시 프레임 수가 아니다.

MCP 계측을 켠 첫29.153초 MP4는851 decoded 프레임·평균29.19fps·2프레임 초과 간격2개(각351.67ms)였다. 두 긴 공백의 시작6.902초와22.262초는15.36초 간격으로, 계측용 snapshot 경계에 해당한다. 따라서 계측 자체가 메인 루프를 멈출 수 있으며 이 파일을 무간섭 성능 기준으로 사용하지 않는다. 별도 **무간섭**29.025초 MP4는871 decoded 프레임·평균**30.01fps**, PTS 중복0, 66.67ms 초과 간격0, 최장 간격65.0ms, 첫 영상/오디오 PTS 모두0초였다. p50/p95/p99 간격은41.67/43.33/43.33ms로 프레임 페이싱이 균일하다고 단정하지 않는다. 영상은966×1080픽셀이며, 8초 프레임에서 방향·한글·서클/노드 형태를 육안 확인했다. 녹화 중 실제 앱 화면도 방향과 한글이 정상임을 확인했다. encoded 프레임과 decoded 프레임은 이번 녹화에서 모두871개였다.

MIDI 궤도 편집기를 연 채 시작한 별도 녹화의 첫 프레임은 `subviewCaptures=1` fallback으로 생성됐고, 저장된 PNG에서 편집기·노트·한글·방향이 정상으로 보였다. 재생 팔로우가 곧 다른 맥락으로 이동해 이 경로의 지속 녹화 성능은 아직 검증되지 않았다.

별도 **무간섭 109.856초 전환 녹화**에서는3288 decoded 프레임·평균29.93fps, PTS 중복0, 66.67ms 초과 간격0, 최장65.0ms였다. 31·33·65·81초 프레임에서 DJ Intro→Groove→Lift→Club Chorus의 캡션·서클 장면 전환과 한글 방향을 육안 확인했다. 섹션을 가로지르는 파일이 저장되고 프레임 길이 공백은 없었지만, 실제 플레이어 청취·AV 중간/끝 offset을 검증한 것은 아니다.

이 측정은 약29초, 세로 창, 한 프로젝트에 한정한다. 이전 build171의 17.32fps와 창·계측 조건이 달라 단순 개선율을 주장하지 않는다. 실제 compositor FPS, 1920×1080 가로/10분 녹화, AV 중간·끝 offset, 루프 경계, editor subview의 지속 성능, 최소화/복원, 실제 플레이어 청취는 **미검증**이다. 시작 요청에서 일시적인 출력 노드 준비 timeout을 build176·177에서 각각 한 번 보았고 재시도는 성공했다. build179 첫 시도는 정상 시작했다. 출력 신뢰성도 장시간 gate에서 재확인한다.

최종 build179 소스의 전체 Swift 테스트는 **1007개 실행·3개 skip·실패0**이며 Python MCP 테스트35개도 통과했다. 독립 diff 검토는 앞선 라벨 캐시 폭별 증가 문제의 수정을 확인했고, 새 P1/P2를 찾지 못했다. 512개 이상 서로 다른 가시 라벨에서 캐시가 자주 비워질 수 있으므로 고밀도 QA 항목에 남긴다.

남은 필수 gate는 PASS로 처리하지 않는다. 상세 범위는 [0.70.0 계획](0.70.0.md)과 [로드맵](roadmap.md)에 있다.

## build180 · 가로 녹화와 감상 모드 배치

build180 앱에서 녹화 버튼 바로 다음의 감상 모드 버튼을 세로 2행 헤더와 가로 1행 헤더에서 확인했다. 클릭과 `⇧⌘V` 진입, 버튼과 Esc 복귀가 동작했고 감상 모드에서는 캔버스 텍스트와 메인 헤더가 숨겨졌다. 2560pt 가로 창과 `Window > Move & Resize > Left`로 만든 **1280pt 경계 창**의 헤더에서 버튼 겹침을 보지 못했다. 이는 두 native 창 크기의 육안 QA이며 모든 중간 폭을 검사한 결과는 아니다.

가로 창에서 동일한 f0r h3r 곡을 `section/fit/subtle` 팔로우로 녹화했다. `.build/r70-build180-landscape.mp4` SHA-256은 `25aa0114ebc399638d51c85c678b228bf4546e87e5777c3cd629dbcc2d5243da`이다. 저장 파일은 **1920×942, 64.929초, 1939 decoded 프레임**, 평균29.86fps, PTS 중복0, 66.67ms 초과 간격0, 최장65ms, 첫 영상/오디오 PTS0초였다. 이는 가로 파일이지만 **1920×1080 검증은 아니다**. QA 검사기는 모든1939 decoded BGRA 프레임의 보이는 픽셀을 SHA-256으로 비교해, 표시 순서에서 연속 완전 동일 프레임0개를 보고했다. 같은 방식으로 build179의 세로29초/109초 파일도 다시 확인했다. 이미지 해시가 다르다는 사실은 의미 있는 움직임이나 실제 화면 표시 FPS를 증명하지 않는다. AV 중간·끝 동기와 파일 실재생 청취도 별도다.

검사 명령: `swiftc -parse-as-library qa/inspect-movie-timing.swift -o .build/inspect-movie-timing-content` 후 `.build/inspect-movie-timing-content .build/r70-build180-landscape.mp4`. 원본 MP4와 JSON 결과는 Git 추적에서 제외되는 로컬 QA 자료다. 앱 패키지의 ad-hoc 서명 검증 및 UI 구현 독립 리뷰에서 P1/P2 결함은 확인되지 않았다. `qa/inspect-movie-timing.swift`는 영상의 전 프레임 디코드와 해시 계산이 필요하므로 대용량 파일 분석 시간·메모리 사용이 늘어난다. build180 소스의 전체 Swift 테스트는 **1007개 실행·3개 skip·실패0**이었다. Python MCP 테스트35개는 build179 기준이며 이번 UI/검사기 변경 뒤 재실행하지 않았다.

## build180 · 곡 단위 팔로우 추가 실기기 검증과 출고 판단

최종 QA 앱을 재실행하고 동봉 f0r h3r를 Scarlett 6i6 USB 출력으로 재생·정지했다. 오디오 장치에서 재생 시작은 확인했으나 실제 스피커/헤드폰 청취는 사용자 확인을 받지 않았으므로 청취 PASS가 아니다. QA 앱은 세션을 저장하고 종료했다.

곡 단위 팔로우로 추가한 무간섭 가로 MP4 `.build/r70-build180-song-overview.mp4`는 **1912×1080, 25.4307초, 762 decoded 프레임, 평균29.96fps**였다. 세로 MP4 `.build/r70-build180-song-portrait.mp4`는 **670×1080, 23.7667초, 714 decoded 프레임, 평균30.04fps**였다. 둘 다 PTS 기준 2프레임 초과 공백0개이고 연속 픽셀 완전 동일 프레임0개였다. 각각8초 프레임의 곡 궤도·섹션·연결 배치를 육안 확인했고 [README 이미지 출처](../images/README.md)에 기록했다. 가로 영상의 너비는1912픽셀이므로 **정확한1920×1080 gate는 통과하지 않았다**.
