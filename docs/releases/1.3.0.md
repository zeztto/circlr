# 1.3 · 보존·복구와 기본 조작 신뢰성

상태: IN_PROGRESS · 기준: 1.2.0/build253 · branch: `release/1.3.0` · 후보: build259 / 미출고 · [패키지 증거](../../qa/evidence/r130-build259.json)

[2.0까지 상세 계획](2.0-development-plan.md)의 첫 실행 버전이다. 새로운 recovery 시스템을 전면 작성하는 일이 아니라, 기존 저장·복구·미디어 동선을 실제로 재현해 확인된 결손을 고치는 작업이다.

## 목표·제외 범위

편집·저장·재생 중 문제가 나도 마지막 유효 작품을 보존하고 사용자가 복구할 수 있어야 한다. 계정 없이 동작하며, 다음 버전의 녹음 시간을 안전하게 기록할 수 있는 기반을 확정한다.

제외: overdub/count-in 구현, artist catalog, AU 지연 보정, 영상 최적화, 새 음색 확장. 이 영역에서 데이터 손상이나 기존 기능의 심각한 회귀를 발견하면 즉시 차단 결함으로 분리한다.

### 최초 planning gate

1. 현재 main과1.2 source/tag, 작업 중인 checkout·파일 상태를 확인한다. 보호할 사용자 원본을 식별하고 격리 사본을 만든다.
2. 기존 테스트를 읽고 같은 계약을 반복 검증하는 테스트를 새로 만들지 않는다. 실패 재현·경계 조건을 추가한다.
3. QA20건을 아래 matrix에서 구체적인 파일/예상결과로 확정한다. 실제 source 결함이 없으면 ‘신규 기능 구현’이 아니라 검증 완료로 기록한다.
4. 새로운 파일/schema가 필요하면 migration·실패 복구·rollback을 먼저 문서화한다. 스키마 변경이 불필요하면1.2 형식을 유지한다.
5. 버전 시작 branch는 최신main의 `release/1.3.0`이다. 이 계획 작성 단계에서는 branch와 후보 build를 만들지 않는다.

## 검사 명령과 결과 보존

아래는 앞으로 실행할 명령이다. 아직 PASS 결과가 아니다.


버전 전체 통합 검사는 최종 후보에서 한 번 수행하고, 수정이 있으면 영향 범위만 재검증한다. `qa/evidence/r130-*.json`에 기준 build/source·조건·실제 결과·원본/결과 hash·미검증을 남긴다. raw 로그와 QA 음악 파일은 공개 소스에 자동 포함하지 않는다.

## 사용자 검수와 마감

사용자 조작이 필요하기 전까지 자동·MCP·허용된 격리 앱 검증을 완료한다. 한글 IME와 실제 복구 경험에 사용자가 필요하면 테스트 파일·행동 순서·기대 결과를 하나의 검수 묶음으로 제공한다. 실제 IME를 확인하지 못하면 자동 입력 성공으로 대체하지 않는다.

출고 조건: 정의한20개 이상 장애 시나리오, cold reopen, media 재연결/portable copy, 변경된 컨트롤의 native 입력, 독립 리뷰 차단 결함0, 문서·최신 스크린샷, main/tag/정식Release와 원격 asset 확인. 목표를 일부 달성했다고 버전 숫자만 올리지 않는다.

수정 범위가 예상보다 크면1.3 필수 사용자 결과를 다시 정리하고 나머지를1.4 이후 backlog에 넣는다. 단, 데이터 손상·권한 결함이나1.3 필수 복구 실패를 그대로 두고 완료 처리할 수는 없다.

## 착수 기록 · 2026-09-30

기준 main `e74ce5d`에서 `release/1.3.0`을 만들었다. 저장 계층, native 복구/미디어 동선, 편집 상태, QA matrix를 서로 다른 소유자로 배정했다. 사용자 원본과 계정 연결은 변경하지 않는다.

- 누락 미디어가 있는 기존 패키지의 fingerprint 검사와 저장 경로가 재연결 후 덮어쓰기를 막을 수 있다. 변경 감지 보호를 유지하며 복구 계약을 확장한다.

### build255 native와 build256 수정 후보

실제 미디어 사본 저장·진단 저장/취소·사본 cold reopen을 확인했다. 원본/사본 manifest·WAV hash와 revision17이 일치했다. 복구 취소는 원본 bytes를 보존하고, 복구 후 새 위치 저장은 음악 필드와 오디오를 보존했다(화면 크기에 따라 hierarchyView 변경). 상세 증거는 `qa/evidence/r130-build255-native-media.json`이다.

실제 복구 취소→CmdQ에서 복구 선택을 다시 요구하는 종료 회귀를 발견했다. pending recovery와 clean 문서의 종료만 별도 허용해 원본을 보존하고, dirty 문서는 기존 저장/취소 경로를 유지하도록 수정했다. 독립 소스 검토에서 추가 차단 결함은 없었다. 최초 focused test는 NSApplication 초기화 누락으로 crash했고, 테스트 초기화 수정 후 `.build/r130-recovery-termination.log`에서2PASS/0FAIL을 확인했다. 이 결과를 실제 native 종료 성공으로 대체하지 않는다. build256을 새 후보로 빌드하며 같은 취소→종료→재시작을 재검증한다.

실제 build256에서 취소→CmdQ 후 PID4596 종료, 복구 bytes/hash 보존, 새 process 재시작의 동일 복구 제안과 revision17 복구 완료를 확인했다. `qa/evidence/r130-build256.json`에 결과를 기록했다. R06의 이 종료 회귀는 해결되었으며 남은 native/최종 패키지 gate를 완료해야 출고할 수 있다.

## build258 통합 준비

build257 이후 수정: 손상 recovery를 보존한 위치를 실제 경고 창으로 안내하고 Finder에서 확인할 수 있도록 연결했다. 디스크가 가득 차서 staging 정리까지 실패하면 잔류 경로와 원래 오류를 함께 제공한다. 기존 곡을 지우는 cleanup fallback은 추가하지 않았다.

제한된 APFS 볼륨에서 copy/manifest 쓰기의 실제 ENOSPC, 원본 보존, 공간 확보 후 같은 목적지 재시도를 확인했다. 영향 검사 16 PASS·의도적 skip 2, 별도 HFS+ 검사 1 PASS. HFS+ 기존 목적지의 atomic swap은 ENOTSUP으로 안전 실패하며 새 위치 저장만 검증했다. HFS+ overwrite 지원이나 publication 단계 ENOSPC 성공을 주장하지 않는다. [증거](../../qa/evidence/r130-disk-full.json). 독립 코드 검토에서 actionable finding 0건. build258 패키지·native 결과는 별도 기록한다.

통합 결과: build258 빌드·strict/deep ad-hoc 서명 검사 PASS. 격리 앱에서 malformed recovery 경고의 원인·정확한 보존 경로 표시, Finder의 해당 파일 선택, 경고 이후 시작 화면을 확인했다. 보존 bytes SHA-256은 입력 fixture와 동일했다. build257의 경고 비노출 결함은 이 경로에서 해결됐으며 다른 필수 QA가 완료된 것은 아니다.

### build259 migration 복구 안내

지원 불가 schema 복구 실패도 원본 보존 후 정확한 경로와 실제 실패 이유를 표시한다. 보존 회귀 1 PASS, build259 빌드·서명 및 native 복구 선택→migration 거절→보존 안내→startup 복귀, 원본 SHA 동일성 PASS. [증거](../../qa/evidence/r130-build259.json). legacy checksum 확인은 build258에서 명시적 경고·사용자 동의·재연결 완료로 검증했다.
