# 0.70.0 — 재생 비주얼라이저 성능

상태: IN_PROGRESS. 기준0.60.0/build170, branch `release/0.70.0`. 사용자의 2026-09-23 우선순위 변경으로 기존0.70 AI 계정 콘솔은0.80으로 이동한다. 이 버전은 재생 중 낮은 프레임 레이트를 먼저 해결한다.

## 결과와 작업 ID

- R70-01 · 실제 기준선: 격리 QA 앱과 같은 f0r h3r v6 프로젝트에서 재생·팔로우·녹화의 갱신/그리기 비용과 지연을 측정한다. 기존 `frameCount`는 타이머 호출 수이지 표시 FPS가 아님을 구분한다. 앱 build, 디스플레이 크기·Hz, canvas 픽셀, 노드/연결 수, 창 상태, 녹화 유무를 고정한다.
- R70-02 · 핫패스 축소: 기본 곡/섹션 팔로우의 불필요한 참여 서클 탐색 제거, 같은 그리기 프레임의 가시성·context 재사용. 이후 라벨/포트/오디오 시각화 계산은 프로파일 근거가 나온 순서대로 수정한다. 음악 시간·그래프·편집 선택·접근성 결과는 보존한다.
- R70-03 · 계측: main-thread `updatePlaybackFrame`, 캔버스 `draw`, 라벨 배치/포트, 영상 캡처/인코딩 시간을 분리한다. p50/p95/p99·최대 간격 및 dropped/duplicate 프레임을 기록한다. 타이머 호출 수나 인코더의 명목 FPS를 실제 표시 FPS로 보고하지 않는다.
- R70-04 · 실제 검증: 저밀도/고밀도, 가로/세로, 팔로우 target과 전환, 보기 모드, 녹화 없음/있음, 최소화·복원, 정지/재시작, 루프 경계를 확인한다. 1080p/30fps 녹화 파일의 decoded PTS·중복/누락·AV offset과 실제 플레이어 시청/청취를 별도 확인한다.
- R70-05 · 출고: 전체 영향 회귀·독립 검토·한영 문서·새 실제 스크린샷, 패키지/해시와 정식 GitHub Release. 필수 native 프레임 증거가 없으면 RELEASED로 표시하지 않는다.

## 0.60 기준선과 판단 경계

0.60에는 native 표시 FPS 측정이 없다. 당시의 `frameCount`와 `maximumFrameGap`은 timer 호출 진단이며 화면 표시·영상 품질의 증거가 아니다. 현재 코드는60Hz 프레임마다 scene 전체 재탐색, 같은 draw의 반복 가시성·라벨 계산, 전체 redraw를 수행한다. 이것은 소스 기반 병목 가설이며 실제 개선율은 동일 장치의 후보 비교로 결정한다.

초기 목표는 표시 갱신의 p95가 대상 화면 주기 이내, p99·최대 정지와 프레임 누락을 별도 공개하는 것이다. 녹화는1080p/30fps에서 의도치 않은 frame drop/duplicate0, 최대 표시 공백2프레임 이내, 시작/중간/끝 AV offset1프레임 이내라는 기존 R40-04 목표를 이어받는다. 시스템 조건과 측정법을 고정하기 전에는 수치 목표를 통과 처리하지 않는다.

## 순서

1. 0.60 격리 앱으로 재현·프로파일을 남긴다.
2. 각 변경을 작은 범위로 적용하고 audio/music state·focus·AX 불변을 테스트한다.
3. 같은 실제 프로젝트·창 조건에서 후보를 재측정해 병목이 이동했는지 확인한다.
4. 최종 QA·리뷰·문서·릴리스 gate를 닫는다.

AI 계정 콘솔과 프로필/멀티미디어 확장은 로드맵 후속 버전으로 이동하며, f0r h3r의 아티스트 음악 검토는 계속 OPEN이다.

## 1차 실기기 결과 · 2026-09-23

격리 앱의 번들/실행 파일을 확인하고, 동일한 내장 `f0r h3r` 데모(원본 fixture SHA-256 `b15252dbe5d4d4f79b6935449fa7238cf30fe90d783af20544b71ba83fcdf085`) 첫 섹션을 팔로우 `section/fit/subtle`, 녹화 꺼짐으로 재생했다. Mac Studio M4 Max, macOS 26.5.1, LEN P27h-10 2560×1440 @60Hz 디스플레이의 왼쪽 절반 창이다. 0.60 build170 캔버스는 1281×1256, 0.70 **초기 후보** build171은 1280×1256 포인트였다. build171의 선택 포트/라벨 캐시 회귀는 build172에서 수정했다.

| 15초 구간 | 0.60 build170 | 0.70 후보 build171 |
|---|---:|---:|
| 재생 시각 업데이트 콜백 | 235회 / 15.385초 = **15.27Hz** | 854회 / 15.356초 = **55.61Hz** |
| 캔버스 화면 `draw` 콜백 | 이전 버전 계측 없음 | 833회 = **54.25Hz** |
| 후보 `draw` 비용 p50 / p95 / p99 | 이전 버전 계측 없음 | 8.48 / 10.46 / 10.93ms* |
| 후보 시각 업데이트 비용 p50 / p95 / p99 | 이전 버전 계측 없음 | 0.87 / 0.98 / 1.03ms* |

선택 포트의 라벨 겹침 가능성을 수정한 **현재 후보 build172**에서도 같은 첫 섹션(재생16.34–31.70초)의 시각 업데이트는873회/15.364초=56.82Hz, 화면 `draw`는865회=56.30Hz였다. 아래 측정 경계와 녹화 FAIL은 그대로 적용한다.

`sample` 10초 기준 버전에서는 main thread `drawReadableLabels → isVisible → labelContext → contextBounds`가 반복된 병목으로 나타났다. 후보는 그리기 콜백 안에서 `labelContext`, 가시 서클 집합, 포트 연결 방향을 한 번만 계산하고, 기본 팔로우에서 쓰지 않는 참여 서클 탐색을 건너뛴다. 독립 읽기 전용 diff 검토에서 이 경로의 고신뢰 동작 회귀는 발견되지 않았다.

*비용 백분위수는 앱의 최근 600 콜백 버퍼이며 위의 정확한 15초 구간만 뜻하지 않는다. 최대 콜백 간격은 앱 전체 누적값이고 앱 비활성 시간도 포함하므로 구간 지터 증거로 사용하지 않는다. 업데이트/그리기 콜백 Hz는 compositor가 실제 표시한 FPS가 아니다. 후보의 60Hz 표시·섹션 경계 지터·고밀도 장시간 재생·녹화 프레임/AV 동기 검증은 아직 OPEN이다. 따라서 이 수치는 릴리스 gate 통과나 3.64배 실제 FPS 향상 주장으로 쓰지 않는다.

재현: 기준/초기 후보 앱은 각각 `qa/generated/outward-orbit/build170`, `build171`의 `package.json`으로 식별한다. 각 앱에서 내장 데모를 열고 곡 서클을 선택해 재생이 시작된 뒤, `python3 qa/measure-canvas-playback.py --socket "$HOME/Library/Application Support/circlr-integration-qa/Agent/agent.sock" --seconds 15`를 실행한다. QA 앱은 동시에 하나만 켠다. 원격 검토용 수치·입력·검증 경계는 [QA 기록](0.70.0-qa.md)에 보존한다.

### 녹화 동시 실행 · 아직 실패

같은 후보 build171·캔버스에서 녹화 중 10.232초 구간은 시각 업데이트33.81Hz, 화면 `draw`26.29Hz, 영상 `draw`31.27Hz였다. 녹화 UI는 최종 **2995프레임·누락221프레임**을 보고했다. 완성된 173.49초 MP4를 `qa/inspect-movie-timing.swift`로 읽어 표시 순서 PTS를 검사하면 약2999개 샘플, 평균17.32fps, p95 프레임 간격85ms, 2/30초 초과 간격512개로 나타난다. 기록기 내부 카운트와 파일 샘플 개수의 차이도 조사해야 한다. 처음 화면 PTS는0.363초, 오디오는0초였으며 실제 플레이어 시청·청취는 아직 하지 않았다. 이 상태는 R70-04 녹화 gate **FAIL**이다. 화면 녹화를 켜면 별도 캔버스 그리기와 인코딩이 화면 재생과 경쟁하므로, 캡처/인코딩 시간을 분리 계측하고 프레임 페이싱을 개선한 뒤 같은 조건으로 재검증한다.
