## 경로와 G0

QA232가 검증할 경로는 **로그인된 외부 Codex CLI 모델 → circlr-studio 프로젝트 skill → 동봉 stdio MCP adapter → 격리 서명 QA 앱의 일반 AgentSocket → QA 전용 `.circlr` 사본**이다. 이는 사용자가 별도 Codex client를 설치·연결하는 제작 경로다. `Resources/Codex/install.py`는 프로젝트별 `.agents/skills/circlr-studio`, `.codex/agents`, `.codex/config.toml`만 설치하고 전역 인증·모델 설정을 수정하지 않는다. OpenAI 문서도 Codex를 외부 MCP client로 사용하는 stdio 서버와 project-scoped config를 지원한다. 프로젝트 config는 신뢰된 프로젝트일 때만 로드된다. [MCP](https://learn.chatgpt.com/docs/extend/mcp), [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic).

공개 제품의 **앱 내 Codex 계정 대화**는 별도 production G0다. [App Server 공식 문서](https://learn.chatgpt.com/docs/app-server)는 `codex app-server` 명령과 WebSocket transport를 experimental·production workload 미지원이라고 명시한다. [MCP server removal 안내](https://learn.chatgpt.com/docs/mcp-server)는 Codex를 MCP **server**로 제공하는 경로와 Codex의 외부 MCP **client** 지원을 구분한다. 따라서 외부 CLI E2E가 PASS여도 앱 내 로그인·대화·trusted turn·STOP·런타임 재배포의 GO가 아니다. API key/Agents API로 인증·과금을 무언중 바꾸지 않는다. [build226 G0 판단](0.80-build226-codex-g0.md)을 유지한다.

## 격리 endpoint 연결 — 현재 kit의 QA 전용 설정

동봉 `Resources/Codex/skills/circlr-studio/scripts/mcp_server.py`는 기본적으로 `~/Library/Application Support/circlr/Agent/agent.sock`의 `selected.json`을 `EndpointResolver`로 읽는다. 성공한 세션은 socket identity와 `runID`를 pin하고 요청에 `expectedRunID`를 넣는다. 반면 `--socket` 또는 `CIRCLR_SOCKET` 지정은 **legacy 직접 socket 경로**로 들어가 `selected.json`/`runID` pin을 통과하지 않는다. `install.py`의 프로젝트 config에는 QA root 인자가 없다. 실제 QA 앱의 `com.circlr.qa232qa`는 `~/Library/Application Support/circlr-qa232-qa/Agent/`에 연결된다(`RecoveryFileStore.storageDirectoryName`). QA 경로는 아래의 MCP 자식 전용 HOME 설정으로 연결한다. production Support root를 변경하거나 `--socket` 직결 결과를 pinned PASS로 기록하지 않는다.

실행 가능한 QA 경로는 **MCP subprocess에만 fake `HOME`을 주고**, 그 안의 `Library/Application Support/circlr/Agent`를 실제 QA Agent directory에 symlink하는 것이다. Codex 본체의 `HOME`·`CODEX_HOME`·저장된 ChatGPT 로그인은 바꾸지 않는다. MCP의 기본 `EndpointResolver`는 fake HOME 아래의 `selected.json`을 읽고 symlink가 가리키는 QA socket에 연결하므로 pin/`expectedRunID`가 유지된다. OpenAI는 stdio MCP 서버별 `env`를 project `.codex/config.toml`에서 지정하도록 문서화한다. [MCP](https://learn.chatgpt.com/docs/extend/mcp), [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic).

이를 동봉 adapter import + 임시 UNIX socket/`selected.json` fixture로 시험했다. private fake HOME의 Agent symlink를 통해 `rpc()`가 `CIRCLR/2 <runID>` framing과 JSON `expectedRunID`를 실제로 전송하고 응답 뒤 socket identity/runID를 pin했다. **같은 경로의 socket을 교체하자 `target_changed`로 거절**했다. 모델/실제 앱/네트워크는 사용하지 않았다. 첫 시험의 긴 `/tmp` 경로는 macOS `AF_UNIX path too long`으로 실패했다. fake HOME은 `mktemp -d /tmp/cq232.XXXXXX`처럼 짧은 경로여야 하고 연결에 쓰일 fake socket 경로의 UTF-8 길이를 시작 전에 검사해야 한다. symlink는 QA 전용이며 실제 Agent directory·socket·`selected.json` 모두 같은 UID, private 디렉터리, `selected.json` mode `0600`인지 확인한다. `EndpointResolver`가 `bundleID`를 기대한 QA ID와 비교하는 코드는 없으므로, 모델 turn 전 `selected.json`의 `bundleID/runID/endpoint`와 앱 snapshot의 세 값을 별도로 대조한다. symlink나 대상이 바뀌면 기존 MCP 세션을 종료하고 새 세션으로 시작한다. 이는 같은 OS 사용자 내 **QA 라우팅**이며 제품 배포용 인증 경계가 아니다.

## 단일 E2E 실행 절차 — 격리 앱 준비 뒤

1. 같은 소스/build의 `dist/써클러.app`과 Codex kit 25개 manifest hash, `codesign --verify --deep --strict`를 확인한다. 앱을 Git-ignored `qa/generated/r80-qa232-model-native/`에 `ditto`로 복제해 bundle ID `com.circlr.qa232qa`로 바꾸고 ad-hoc 재서명한다. `CFBundleVersion`과 QA 앱 실행 파일 hash를 기록한다. 사용자 앱·원본 데모·기존 `circlr-integration-qa`는 열거나 변경하지 않는다. bundle ID에 대응하는 Support root는 `~/Library/Application Support/circlr-qa232-qa`여야 한다.
2. QA 앱의 번들 데모를 **새** `Support/fixtures/<고유명>.circlr`에 복사한다. source/fixture의 manifest와 전체 파일 hash를 편집 전 기록한다. 같은 project ID를 유지해도 전용 bundle/Support와 문서 경로로 원본을 분리할 수 있으며, 새 ID로 바꾸면 그 변경을 초기 hash와 함께 기록한다. 모델용 사본과 결정적 script용 사본을 분리한다. 앱에서 모델용 사본을 열고 dirty=false, `runtime.bundleID`, `runtime.build`, `runtime.runID`, `runtime.agentEndpoint`, `projectID`, `revision`, `path`를 `circlr_snapshot`과 앱 측 activity로 대조한다. `Agent/selected.json`의 `bundleID/runID/endpoint`가 snapshot과 같고 선택 socket이 같은 UID의 socket인지 읽기 전용으로 확인한다.
3. 별도 Git-ignored Codex client directory를 만들고 **서명 QA 앱 안의** `Contents/Resources/Codex/install.py`를 `python3`(현 Mac 3.14.4)으로 `--dry-run`, 이어 실제 `--project <QA-client-dir> --python /usr/bin/python3`로 실행한다. `/usr/bin/python3`는 3.9.6으로 adapter 실행은 되지만 `tomllib`이 없어 installer 실행에는 쓰면 안 된다. 설치 결과의 skill/agent/config 경로, manifest version과 hash를 대조한다. `mktemp -d /tmp/cq232.XXXXXX`로 mode `0700`의 짧은 `QA_FAKE_HOME`을 만들고 그 안에 `Library/Application Support/circlr` 디렉터리를 만든 후, `Agent`만 `~/Library/Application Support/circlr-qa232-qa/Agent`로 symlink한다. `readlink`로 정확한 QA root를 확인한다. **설치된 QA client의** `.codex/config.toml`의 `[mcp_servers.circlr]`에 `env = { HOME = "<실제 QA_FAKE_HOME 절대 경로>" }`를 더한다. `--socket`/`CIRCLR_SOCKET`은 지정하지 않는다. installer 관리 파일을 QA용으로 수정했으므로 같은 client에서 installer 재실행 전에는 config hash/state를 먼저 정리해야 한다. 전역 `~/.codex/config.toml`은 수정하지 않는다.
4. 해당 client directory에서 `codex -C <QA-client-dir> -c 'mcp_servers.circlr={...QA adapter/env...}' mcp list`로 서버가 **동봉 adapter의 QA 인스턴스 하나**이며 `env.HOME`이 fake HOME인지 확인한다. 실제 QA에서는 project config가 단독으로 `mcp list`에 나타나지 않아 같은 값의 CLI `-c` override를 사용했다. `--ignore-user-config`는 `codex exec` 옵션이며 `mcp list`에 전달하지 않는다. 이 옵션은 사용자의 `config.toml`을 배제하지만 인증은 기존 `CODEX_HOME`을 사용한다(`codex exec --help`의 현지 결과). `codex login status`를 재확인하고 API key 환경변수를 주입하지 않는다. 모델 ID를 명시하지 않으면 CLI 기본 모델을 사용하며 정확한 ID는 trace에 나타나지 않을 수 있다.
5. 모델용 fixture의 실제 arrangement/use/lane/track ID와 음악 문맥을 먼저 inspect한 뒤, **한 MIDI lane의 지정한 마지막 2마디에 응답구를 추가하되 기존 melody/다른 section은 보존**하도록 한 turn을 요청한다. 모델은 `snapshot → inspect → apply(projectID, expectedRevision) → inspect → undo → inspect → 재apply(새 revision) → inspect → bounce/job → export/job → save → open/job → snapshot/inspect`의 실제 `circlr_*` 호출을 사용한다. 각 async job은 terminal `completed`를 확인한다. stale revision은 원 요청을 그대로 재제출하지 않고 재inspect해야 한다. `circlr_cancel_job`은 job만 취소하며 앱 소유 trusted STOP이 아니다. [동봉 session contract](../Resources/Codex/skills/circlr-studio/references/session-contract.md), [operations](../Resources/Codex/skills/circlr-studio/references/circlr-operations.md). 실행 전 `<...>`를 실제 QA snapshot/inspect 값으로 채운 prompt 파일의 본문은 다음과 같다.

   ```text
   $circlr-studio를 사용하세요. 지금 열린 QA 프로젝트 <projectID>, revision <N>의
   <arrangementID>/<useID>에서 <laneID> 한 곳의 마지막 2마디에 짧은 응답구를 만드세요.
   기존 멜로디 노트와 다른 use/section/track은 보존하세요. 먼저 snapshot과 inspect로
   실제 ID·박자·음역·악기 역할을 확인하고, 의도와 편집 범위를 한 문장으로 설명하세요.
   circlr_apply 한 batch 뒤 inspect, circlr_undo 뒤 정확한 원복, 새 revision으로 재적용을
   확인하세요. 그다음 해당 track bounce/job, QA root 안의 신규 WAV export/job,
   save, 같은 QA 문서 open/job 및 최종 inspect를 수행하세요. 모든 write는 circlr MCP만
   사용하세요. stale_revision이면 재검토하고, 임의 경로의 파일/사용자 프로젝트는 열지 마세요.
   실제 호출 결과와 검증하지 못한 청취 항목을 분리해 보고하세요.
   ```

6. trace는 `codex exec --json --ephemeral --ignore-user-config`의 stdout JSONL을 QA 전용 evidence로 저장한다. 실제 첫 시도는 `-s read-only`/approval `never`에서 MCP `apply`가 거절됐고 revision 불변을 확인했다. 쓰기가 필요한 두 번째 시도는 QA fixture 경로만 `--add-dir`로 추가하고 `--approve-for-me`를 사용했다. `--approve-for-me`와 `-s`는 현 CLI에서 함께 지정할 수 없다. 같은 QA MCP config를 `-c`로 명시했다. 자동 승인 결과와 tool/job 결과를 독립 검증하며, 모델 최종 답변만으로 PASS로 쓰지 않는다. [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode). 실행 전 fake HOME/socket 경로 길이와 승인 정책을 기록한다.

   ```sh
   codex exec --json --ephemeral --ignore-user-config \
     -C "$QA_CLIENT_DIR" --add-dir "$QA_FIXTURES_DIR" --approve-for-me \
     -c 'mcp_servers.circlr={...QA adapter/env...}' - \
     < "$QA_EVIDENCE_DIR/prompt.txt" > "$QA_EVIDENCE_DIR/codex.jsonl" \
     2> "$QA_EVIDENCE_DIR/codex.stderr.log"
   ```
7. 별도 결정적 fixture에는 `python3 qa/verify-agent-journey.py --project <QA-fixture.circlr> --evidence <신규 QA evidence> --build <실제 build> --qa-root "$HOME/Library/Application Support/circlr-qa232-qa" --bundle-id com.circlr.qa232qa`를 실행할 수 있다. 이는 도구/앱 계약 대조용이며 **모델 E2E의 대체가 아니다**. 이 스크립트는 `mcp/server.py --socket` 직접 연결이라 pinned resolver도 검증하지 않는다. 기존 evidence/export가 있으면 거부하므로 매 실행 새 이름을 쓴다.

## 합격 판정과 기록

- 모델/CLI 버전, 인증 **방식만**, model ID(확인 가능하면), QA app bundle ID/build/runID, pinned endpoint basename/socket identity, kit manifest hash, client config hash, fixture 전후 SHA-256, Codex JSONL, 앱 activity와 job 상태를 함께 보존한다. 인증 토큰·계정 식별자·사용자 프로젝트 내용은 기록하지 않는다.
- tool trace에서 실제 `circlr_snapshot/inspect/apply/undo/bounce/job/export/save/open` 호출 및 성공/실패 순서를 확인한다. 모델의 note 위치·pitch·length·velocity·음악적 역할을 inspect 전후 diff로 평가하고, 기존 melody/비대상 section/트랙의 데이터와 hash 보존을 확인한다. Undo 뒤 정확히 원복, 재적용 뒤 revision 증가와 저장·재열기 동일성을 확인한다.
- export는 QA root 안의 신규 WAV이며 헤더 48 kHz/stereo/24-bit, 1초 초과 frames, nonzero PCM 및 SHA-256을 확인한다. bounce는 `job.state=completed`, 새 `nodeID`, 경로/라우팅 inspect와 저장·재열기로 확인한다. 앱 activity의 요청·job과 JSONL의 MCP tool을 시간/ID로 대조한다. 실제 청취·음악적 출시 품질은 이 기계적 PASS와 별도다.
- 다른 run/socket으로 바뀌면 pinned 세션이 `target_changed`로 멈추고 재연결하도록 시험한다. 외부 MCP는 같은 OS 사용자 권한으로 동작하므로 이 결과를 trusted turn의 STOP·TTL·문서 권한 증명으로 확대하지 않는다. 실패나 중단 시 현재 snapshot/manifest를 먼저 확보하고 같은 write를 blind retry하지 않는다.

후속 판정은 [실제 build230 모델 QA](0.80-qa232-model-native.md)에 있다. 네 note 편집·Undo·저장/재열기·WAV의 제한된 외부 CLI 경로는 PASS다. 이 문서의 더 넓은 bounce/모델 ID/STOP 시나리오와 앱 내 계정 콘솔은 미검증이다.
