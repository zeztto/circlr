[build217](0.80-build217.md)은 Open·저장·재열기 native 동선이 통과했지만, 후속 저장 보안 리뷰에서 일반 폴더의 유효 manifest 옆 개인 파일을 덮어쓰기로 지울 수 있고 FIFO manifest 읽기가 멈출 수 있음을 발견해 출고 후보에서 제외했다. build218은 저장 전 기존 폴더의 소유 파일을 검사하고, manifest를 `O_NOFOLLOW|O_NONBLOCK`으로 열어 일반 파일과 크기 상한을 확인한다. 기존 사본 정리는 package 내부 디렉터리 fd 아래 `unlinkat`으로만 하므로 중간 symlink가 외부 경로를 가리켜도 그 밖의 파일을 지우지 않는다. 새 곡 저장이 이미 완료된 뒤 사본 정리에 실패하면 오류 대신 경고를 돌려 GUI·agent의 `projectURL`, `mediaRoot`, `dirty`가 디스크의 저장 완료와 일치한다.

`swift test`는 **1,186개 중 14개 skip, 실패 0, 종료 코드 0**이었다. skip에는 opt-in 실기기/환경 테스트가 포함된다. 일반 폴더의 `notes.txt`와 manifest가 저장 거절 뒤 바이트 단위로 보존되고 staging/backup이 남지 않는 경우, manifest 파일 직접 열기, FIFO 즉시 거절을 `CoreTests`가 검증했다. `./scripts/build-app.sh`로 0.80.0/build218 arm64 앱과 오디오 helper 5개·agent kit을 패키징했고, `codesign --verify --deep --strict`가 통과했다. 패키지 실행 파일 SHA-256은 `881493bc005b1926cc4e1148e71406f449dd275392e184bd695dfbab580e213b`다. 기존 `PlaybackFollowCameraCurve` Sendable 경고가 출력됐지만 빌드 실패는 없었다. Python MCP/agent kit 소스는 변경하지 않아 이전 실행 결과를 build218 결과로 재기록하지 않는다.

읽기 전용 저장 보안 재검토에서는 fd 경로와 저장 후 상태 분리에서 새 고확신 P1/P2를 찾지 못했다. 정리 실패/부분 백업 경고 경로는 직접 결함 주입 테스트가 없으며, 다른 프로세스가 저장 중 동일한 소유 미디어 파일명을 교체하는 기존 동시쓰기 경합도 해결하지 않았다. 일반 사용자의 별도 개인 파일 보존 테스트와 구분한다.

[실제 build218 앱](0.80-build218-native.md)에서는 QA manifest 직접 열기는 성공했지만 첫 `⌘S`가 `FileManager.copyItem → clonefileat`에서 30초 이상 반환되지 않았다. 원본 데모·QA 프로젝트·일반 폴더 파일과 시스템 기본 출력은 불변이었고 격리 앱/helper는 종료했다. GUI의 폴더 재열기·개인 파일 덮어쓰기 거절은 이 빌드에서 미실행이다. build219에서 미디어 복사를 청크 읽기/쓰기로 바꾸고 동일 동선을 재검증한다. Scarlett 6i6 USB의 세대는 이 환경에서 확인하지 않았고, 별도의 CalDigit 선택 입력도 시작 단계 timeout으로 PCM을 얻지 못했다. 따라서 이 빌드의 오디오 입출력 성공이나 물리 청취를 주장하지 않는다. `v0.80.0` tag와 GitHub Release는 만들지 않는다.
