build225의 전체 Swift에서 `AudioTests.testVirtualMIDIReceivesMultiplePackets`가 `MIDI client 생성 실패: -2`로 실패했다. 독립 scratch의 좁은 재현에서도 `AppOwnedAgentTurnIntegrationTests` 5개 → `AudioClipEditingTests` 8개 → `AudioTests` 7개 순서가 실패했다. `AppOwned`→`AudioTests`, `AudioClipEditing`→`AudioTests`, `AudioTests` 단독은 각각 통과했다. `AppOwned` 뒤 8초만 쉬고 `AudioTests`를 실행하면 실패했고, 같은 시점의 순수 `MIDIClientCreate`도 `-2`였다. 실패 뒤 즉시 두 번째 `MIDIClientCreate`를 호출해도 `-2`였으므로 짧은 재시도를 해결책으로 쓰지 않았다.

같은 Mac의 별도 단일 프로세스 CoreMIDI harness에서 `MIDIClientCreateWithBlock`→input port/virtual destination 생성→endpoint/port/client dispose→10초 idle→client 재생성은 `0, -2`였다. 첫 client만 유지하고 endpoint/port를 정리한 채 10초 idle 뒤 두 번째 client를 만들면 `0, 0`이었다. `launchctl print gui/$(id -u)/com.apple.midiserver`를 읽기 전용으로 관찰했을 때 실패 경로에서 서버는 `running`에서 `not running`으로 바뀌었고 `last exit code = 0`이었다. 이 증거는 이 호스트에서 **마지막 client 해제 후 서버가 끝난 상태의 동일 프로세스 재연결 실패**를 보여준다. 모든 macOS 버전이나 모든 MIDI 장치의 동작이라고 일반화하지 않는다.

`MIDIInput`은 이제 process lifetime 동안 하나의 CoreMIDI client를 `NSLock`으로 보호해 공유한다. 각 `MIDIInput` 인스턴스의 input port와 virtual destination은 이전처럼 `deinit`에서 해제한다. 최초 client 생성 실패는 오류로 전달하며 성공한 client만 보관한다. 이 변경은 앱 내 MIDI 재진입 시 서버 idle 종료로 같은 프로세스가 입력을 잃는 경계를 줄인다. 오디오 출력 장치나 시스템 기본 장치 설정은 건드리지 않았다.
