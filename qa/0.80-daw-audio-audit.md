# 0.80 build221 · DAW 오프라인 제작 경로 감사

2026-09-24 · `release/0.80.0`의 `3d44995`에서 시행. **검사한 오프라인 경로 통과 / 1.0 음악 제작 및 0.80 릴리스 승인 아님.** 사용자 프로젝트·시스템 오디오 장치는 변경하지 않았다. 생성 WAV, section stems, 상세 로그는 Git 제외 `qa/generated/r80-daw-audio/`에 보존했다.

## 실제 실행

```sh
swift build -c debug --product circlr-studio
swift test -c debug --filter 'SequentialStemExportTests|WAVExportTransactionTests|StepEditingTests|AudioEditingTests|MIDIPitchBendExportRoundTripTests'
.build/debug/circlr-studio render Resources/Demos/classical/bach-invention-08/bach-invention-08.circlr qa/generated/r80-daw-audio/bach-invention-08.wav
.build/debug/circlr-studio section-stems Resources/Demos/classical/bach-invention-08/bach-invention-08.circlr qa/generated/r80-daw-audio/bach-section0-stems 0
```

대상 Swift 테스트는 **41개 실행, 실패 0, skip 1**이다. skip은 `CIRCLR_QA_STEM_PROJECT`/`CIRCLR_QA_STEM_OUTPUT`이 필요한 별도 16트랙 native fixture 시험이다. 나머지 테스트는 MIDI step 및 오디오 편집, pitch bend MIDI round-trip, 순차 stems/sidechain, WAV 원자 교체와 STOP 경계를 다룬다. raw 출력은 `qa/generated/r80-daw-audio/targeted-tests.log`다.

번들 Bach 프로젝트의 `manifest.json` SHA-256은 실행 전후 `a0350b4802b192bf3d7ba207a9a031f166c0c5092e60faf0f82f766da3257c34`로 같았다. 이 곡은 4개 섹션, 2개 트랙이다. CLI의 `render`는 이 프로젝트를 읽어 album plan을 내보냈다.

| PCM | peak 2,092,075 / 8,388,607, RMS 412,092 / 8,388,608; 0–70초의 각 10초 구간 모두 nonzero |

각 WAV header/PCM을 Python `wave`와 NumPy로 독립 파싱했고 `render-report.json`, `bach-section0-stems/manifest.json` 및 `render.log`를 남겼다. 이전 build185의 native MCP QA는 step 추가→Undo→FX/automation→track bounce→fade→저장·재열기→WAV와 실제 PCM 차이를 확인했다([증거](0.80-offline-daw-journey.md)); 이번 build221 재시험은 **순수 source CLI의 render와 section stems** 및 위 대상 테스트이므로 native 앱 편집·저장·재열기 재현으로 확대 해석하지 않는다.

## 미해결 위험과 다음 수정

이번 오프라인 경로에서 새 P1/P2 결함은 재현되지 않았다. 다만 **실제 오디오 take 기록은 이 검사로 보장할 수 없다**. `Sources/CirclrAudio/AudioRecorder.swift`의 `EngineCaptureBackend.start`가 `AVAudioEngine.inputNode`를 동기로 획득한다. 드라이버/HAL이 반환하지 않으면 `AudioRecorder.start`의 10초 timeout은 UI 응답을 돌려주지만, `CaptureAttempt.finish`가 같은 serial queue 뒤에 쌓여 `attempt` 정리가 끝나지 않는다. 따라서 `busy`가 남아 같은 앱 프로세스에서 녹음을 재시도할 수 없는 위험이 있다. 이는 코드 경계와 이 호스트의 이전 input/output HAL hang 관찰을 결합한 **위험 추론**이며, 이번에 Scarlett에서 마이크 take를 실행해 재현한 결함은 아니다. `qa/0.80-selected-input-investigation.md`도 CalDigit 선택 입력에서 두 API 경로가 멈췄지만 PCM을 얻지 못했다고 기록한다. 구형 Scarlett이 원인이라고 단정하지 않는다.

효과가 큰 다음 수정은 `AudioRecorder`의 동기 장치 준비를 종료 가능한 별도 capture helper 경계로 옮기고, timeout/취소 후 helper 종료·부분 take 격리·새 장치 재시도 계약을 검사하는 것이다. 관련 source는 `Sources/CirclrAudio/AudioRecorder.swift`, `Sources/CirclrAudio/CaptureControl.swift`, `Sources/CirclrApp/AppStore.swift`의 `startAudioRecording`/`finishAudioRecording`이다. 이 수정은 단순 메시지 변경으로 대체하기 어렵다. 제품 적용 전 사용 가능한 별도 입력에서 실제 nonzero PCM, 종료 후 리소스 정리, 재시도 성공을 확인해야 한다.

음악적 완성도·실제 청취, GUI에서 빈 곡부터 전체 흐름, 녹음 take, AU 호환성, 장시간/반복 메모리, 하드웨어 출력은 **미검증**이다. 현재 호스트의 Scarlett은 구형이므로 검증 기준 장치로 가정하지 않는다.
