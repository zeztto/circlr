상태: **미해결 출고 차단** · 2026-09-23 · 격리 QA 앱 0.80.0/build184 (`appSHA256 df43e4604eb50680e574f2e3a03accd66bc836d6e884054fade157037e26483f`)와 build185 ([앱 검증 기록](0.80-build185.md)). 시스템 출력 설정이나 사용자 프로젝트는 변경하지 않았다.

## 관찰

- build182의 Scarlett 6i6 USB와 Mac Studio 스피커에서는 준비 제한 시간 약 10초가 재현됐다. 같은 build182를 독립 재검사한 helper 무음 1초 CAF는 자연 종료했고, 앱 재생·정지는 두 장치에서 상태 전이에 도달했다. build183의 f0r h3r는 Scarlett 출력 시작·약 32초 재생·정지에 도달했다. 물리 청취는 이번 조사 범위 밖이다.
- build184의 Invention 8 영상 녹화는 같은 QA 앱에서 4회 시도 모두 출력 준비 timeout으로 끝났다. 선택은 앱의 `systemDefault`였고 최종 MP4나 `.circlr-movie-*.mp4` 임시 파일이 없었다. 영화 캡처 tick도 0회다. 이는 정상 녹화 성공의 증거가 아니다.
- 마지막 session `D021E0F5-3F70-4751-9ABB-936D1E5A8395`의 helper PID 35840 trace는 CAF 작성·helper hello·입력 파일 검증·engine 생성까지 0.03035초에 완료됐다. 다음 `outputNodeAcquisition/entered`에는 완료 이벤트가 없고 요청은 약 10초 뒤 `timedOut`, `didStart=false`였다.
- 같은 PID를 timeout 전에 1초 `sample`한 880개 main-thread stack은 모두 `OutputWorkerService.swift:143 → AVAudioEngine.outputNode → AudioComponentInstanceNew → AudioDeviceCreateIOProcID → HALC_ProxyIOContext::_TellServerAboutStreamUsage → HALC_ProxyObject::SetPropertyData → mach_msg2_trap`이었다. 장치 binding·mixer·`engine.start`·영상 writer 이전의 CoreAudio/HAL 응답 대기다.
- 같은 build184 QA 앱의 후속 1회는 Scarlett 6i6 USB에서 출력 시작·약 4.63초 MP4 저장까지 완료됐다([영상 QA](0.80-short-movie.md)). 이전 네 번의 timeout과 성공 1회가 공존하므로 간헐성 판단은 유지한다. 성공한 파일은 HAL 대기의 원인을 밝히거나 다음 재시도 성공을 보장하지 않는다.
- build185 Bach 격리 QA 앱에서는 Play 요청 3회가 출력 노드 준비 단계에서 약 10초 뒤 timeout으로 끝났고, 설정 화면의 네 번째 요청은 준비 중 수동 취소했다. 각 출력 worker의 CoreAudio 로그는 `SelectDevice: connecting device 111` 다음 `IsDeviceUsable: Device ID: 111 (Input:No | Output:Yes): true`까지 기록한다. 장치 ID의 실제 이름이나 이 로그 뒤의 정지 원인은 확인되지 않았다. 이 로그만으로 드라이버·권한·앱 중 어느 쪽을 원인으로 단정하지 않는다. [build185 QA](0.80-build185.md).

- build185에 동봉된 출력 worker로 1초 무음 CAF를 `systemDefault`와 `deviceUID(BuiltInSpeakerDevice)`에 각각 지정해 독립 실행했다. 두 경우 모두 `fileValidation`·`engineCreation`을 완료하고 `outputNodeAcquisition/entered` 뒤 12초 동안 응답이 없어 해당 child만 EOF로 정리했다. [기계 판독 결과](evidence/r80-build185-silent-output-probe.json). 현재 구현은 명시적 장치 binding보다 `AVAudioEngine.outputNode`를 먼저 얻으므로, 내장 스피커 지정만으로 기본 장치 초기화 지연을 우회할 수 없다. 이는 **현재 호스트·빌드의 두 시도**이며 다른 장치에서의 성공/실패를 예측하지 않는다.
- circlr 코드를 포함하지 않은 최소 Swift 프로세스에서도 `AVAudioEngine()` 생성 직후 `engine.outputNode` 접근 전에 stderr 표시를 남겼고, 이후 표시 없이 12초 제한 시간에 종료됐다. 앱의 곡 렌더링·UI·MCP 없이도 같은 API 경계에서 재현됐으므로 이 호스트의 CoreAudio/AVFAudio 경로 문제라는 판단이 강해졌다. OS나 장치의 정확한 결함은 아직 미확정이다.
- 다른 최소 프로세스의 `AVAudioPlayer`도 1초 무음 WAV를 열었으나 `prepareToPlay()` 전에 남긴 표시 뒤 12초 동안 응답하지 않았다. 이는 `AVAudioEngine`만을 다른 AVFAudio 플레이어로 교체해 해결된다는 가설을 지지하지 않는다.
- [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html)의 AUHAL 생성 순서를 따르는 [제한 시간 진단기](diagnose-auhal-creation.py)를 추가했다. 내장 스피커(ID 76)와 Scarlett(ID 111)의 UID 조회·컴포넌트 검색은 완료됐지만 두 프로세스 모두 **명시적 장치 지정 이전의 `AudioComponentInstanceNew`**에서 10초 timeout이었다. [원자료](evidence/r80-build185-auhal-creation.json). 직접 AUHAL 출력도 이 호스트에서 입증된 우회 경로가 아니므로 제품 출력 backend를 교체하지 않는다.
- [Apple의 직접 IOProc API](https://developer.apple.com/documentation/coreaudio/audiodevicecreateioprocidwithblock%28_%3A_%3A_%3A_%3A%29)에 기반한 [무음 진단기](diagnose-direct-ioproc.py)에서는 출력 buffer를 명시적으로 0으로 채웠다. **내장 스피커 ID 76의 IOProc 생성→시작→정지→해제**는 0.74초/OSStatus 0으로 끝났고, **Scarlett ID 111은 IOProc 생성에서 10초 timeout**이었다. [원자료](evidence/r80-build185-direct-ioproc.json). 이는 시스템 기본 출력을 변경하지 않고 선택 장치로 직접 I/O를 열 수 있는지의 제한된 관찰이다. 실제 곡 PCM 재생, 형식 변환, 루프 경계, 장치 변경, 사운드 청취는 검증하지 않았다.
- 이 Mac은 **macOS 26.5.1**이고 `Scarlett 6i6 USB`가 시스템 기본 출력이다. [Focusrite의 macOS 26 호환성 표](https://support.focusrite.com/hc/ko/articles/12033372452754-macOS%EC%97%90%EC%84%9C-Focusrite-%ED%98%B8%ED%99%98%EC%84%B1)는 Scarlett 2세대를 지원 대상으로, 1세대 6i6은 오디오 class-compliant 동작 가능하지만 Scarlett Mix Control은 동작하지 않는다고 적는다. 이 장치의 세대는 USB 표시 이름만으로 확정하지 않았다. 현상은 이 호스트의 Scarlett 경로에 집중되지만, 단지 구형이라는 이유로 공식 미지원 또는 하드웨어 고장이라고 결론내리지 않는다.

## 판정과 후속

현재 증거는 worker의 `outputNode` 획득 중 HAL IPC 대기를 특정한다. 최소 재현과 무음 probe는 앱 자체의 음악·영상 처리 없이도 이 단계가 멈출 수 있음을 보여준다. 직접 AUHAL의 컴포넌트 생성도 장치 binding 전에 지연되지만, **내장 장치 직접 IOProc만은 시작/정지가 됐다.** 이를 제품 fallback이라고 부르려면 현재 renderer의 48kHz stereo PCM을 장치 형식에 맞춰 실시간 안전하게 공급하고, 프레임 시계·루프 변경·취소·장치 재연결을 같은 의미로 구현·검증해야 한다. Scarlett의 생성 지연과 HAL 서버 측 정확한 원인은 여전히 미확정이다. timeout을 늘리거나 UI 스레드로 장치 획득을 옮기는 변경은 근거가 없다. 기존 helper 격리·사용자 취소·정리 동작을 유지한다.

다음 재현은 같은 final 빌드에서 내장/Scarlett별 cold start와 연속 Play/Stop을 나눠 기록하고, 멈춘 session의 helper 및 관련 CoreAudio 서버 시점·장치 변경 이벤트를 함께 수집한다. 성공한 출력은 실제 청취와 helper 정리를 별도 확인한다. 그 뒤 같은 앱에서 5–10초 MP4와 오디오/영상 프레임 검사를 진행한다. 두 장치 반복 성공 및 실패 뒤 복구가 확인되기 전에는 0.80 출고를 승인하지 않는다.
