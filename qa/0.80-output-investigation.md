# 0.80 출력 준비 간헐 중단 · build184–190

상태: **미해결 출고 차단** · 2026-09-23 · 격리 QA 앱 0.80.0/build184 (`appSHA256 df43e4604eb50680e574f2e3a03accd66bc836d6e884054fade157037e26483f`)와 build185 ([앱 검증 기록](0.80-build185.md)). build184–185에서는 시스템 출력 설정을 바꾸지 않았다. build186의 자동 복원 진단에서만 기본 출력을 잠시 내장 스피커로 바꾼 뒤 원래 Scarlett로 돌렸다. 사용자 프로젝트는 변경하지 않았다.

- circlr 코드를 포함하지 않은 최소 Swift 프로세스에서도 `AVAudioEngine()` 생성 직후 `engine.outputNode` 접근 전에 stderr 표시를 남겼고, 이후 표시 없이 12초 제한 시간에 종료됐다. 앱의 곡 렌더링·UI·MCP 없이도 같은 API 경계에서 재현됐으므로 이 호스트의 CoreAudio/AVFAudio 경로 문제라는 판단이 강해졌다. OS나 장치의 정확한 결함은 아직 미확정이다.
- 다른 최소 프로세스의 `AVAudioPlayer`도 1초 무음 WAV를 열었으나 `prepareToPlay()` 전에 남긴 표시 뒤 12초 동안 응답하지 않았다. 이는 `AVAudioEngine`만을 다른 AVFAudio 플레이어로 교체해 해결된다는 가설을 지지하지 않는다.
- [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html)의 AUHAL 생성 순서를 따르는 [제한 시간 진단기](diagnose-auhal-creation.py)를 추가했다. 내장 스피커(ID 76)와 Scarlett(ID 111)의 UID 조회·컴포넌트 검색은 완료됐지만 두 프로세스 모두 **명시적 장치 지정 이전의 `AudioComponentInstanceNew`**에서 10초 timeout이었다. [원자료](evidence/r80-build185-auhal-creation.json). 직접 AUHAL 출력도 이 호스트에서 입증된 우회 경로가 아니므로 제품 출력 backend를 교체하지 않는다.
- [Apple의 직접 IOProc API](https://developer.apple.com/documentation/coreaudio/audiodevicecreateioprocidwithblock%28_%3A_%3A_%3A_%3A%29)에 기반한 [무음 진단기](diagnose-direct-ioproc.py)에서는 출력 buffer를 명시적으로 0으로 채웠다. **내장 스피커 ID 76의 IOProc 생성→시작→정지→해제**는 0.74초/OSStatus 0으로 끝났고, **Scarlett ID 111은 IOProc 생성에서 10초 timeout**이었다. [원자료](evidence/r80-build185-direct-ioproc.json). 이는 시스템 기본 출력을 변경하지 않고 선택 장치로 직접 I/O를 열 수 있는지의 제한된 관찰이다. 실제 곡 PCM 재생, 형식 변환, 루프 경계, 장치 변경, 사운드 청취는 검증하지 않았다.
- 이 Mac은 **macOS 26.5.1**이고 `Scarlett 6i6 USB`가 시스템 기본 출력이다. ## build186의 장치 경계 분리

- [자동 복원 진단](diagnose-default-output.py)은 변경 전 기본 장치 UID를 정확히 확인하고, 내장 스피커로 잠시 전환해 별도 무음 child를 실행한 뒤 `finally`에서 원래 장치로 복원·재확인했다. 공개 [증거](evidence/r80-build186-temporary-default-worker.json)의 UID는 hash만 남겼다. Scarlett 기본 상태에서 최소 AVAudioEngine은 `outputNode` 획득 전에 10초 timeout이었다. 내장 스피커 기본 상태에서는 `outputNode`→`engine.start`→`player.play`→stop이 0.33초에 끝났다.
- 같은 내장 기본 상태에서 **실제 build186 출력 worker**가 3초 무음 파일을 준비해 `outputNode`·장치 확인·engine 시작·player 시작·재생 clock·stop·parent EOF 종료를 모두 완료했다. 시스템 기본 출력은 진단 후 원래 Scarlett ID 111로 복원됐다. 이는 앱이 생성한 음악의 실제 청취나 Scarlett 출력 성공이 아니다.
- 기본 Scarlett 설정을 **그대로 둔 별도 child**의 [AudioQueue 무음 probe](diagnose-audioqueue-device.py)는 `AudioQueueNewOutput` 이후 명시적 내장 스피커 UID binding→Start→Stop→Dispose를 0.384초에 완료했다. 기본 장치와 명시적 Scarlett은 `AudioQueueStart`에서 각각 8초 timeout이었다. [증거](evidence/r80-build186-audioqueue-devices.json). AudioQueue가 앱 전용 내장 출력의 가능한 backend임은 보였지만, 긴 곡 PCM 스트리밍·루프·장치 변경·실제 청취까지 입증한 것은 아니다.
- 이 차이는 현재 호스트에서 **기본 Scarlett 경로가 AVAudioEngine 초기화에 영향을 준다**는 강한 증거다. Scarlett 기기의 세대, 드라이버 결함, macOS 결함 중 무엇이 근본 원인인지는 미확정이다. 제품에서 시스템 기본 출력을 자동 변경해서는 안 된다. 명시적 내장 출력은 per-app AudioQueue backend와 worker timeout/취소 계약으로 구현·검증해야 한다.
- 사용자 장치가 구형일 가능성은 유력한 조사 가설이지만, 장치 이름만으로 세대를 확정할 수 없다. [Focusrite의 macOS Tahoe 26 호환성 표](https://support.focusrite.com/hc/en-gb/articles/12033372452754-Focusrite-Compatibility-on-macOS)는 Scarlett 2nd Gen을 호환으로 표시하고, 1st Gen 6i6도 class-compliant 오디오는 가능하되 Scarlett Mix Control은 작동하지 않는다고 구분한다. 따라서 현재 timeout을 구형 하드웨어의 확정 결함이나 circlr의 확정 결함 중 하나로 귀속하지 않는다. 실제 세대·연결/clock 상태와 다른 앱의 동일 장치 출력을 함께 확인할 때까지 미확정으로 둔다.

## build187의 명시 장치 출력 경로

- 사용자가 앱 안에서 장치 UID를 명시한 곡·섹션 재생은 AudioQueue를 worker 안에서 사용한다. 시스템 기본 출력을 바꾸지 않는다. `systemDefault`는 기존 AVAudioEngine 경로이므로 이 호스트의 기본 Scarlett에서는 여전히 timeout 가능하다.
- 명시적 내장 스피커를 대상으로 실제 `circlr-output-worker`의 무음 3초 파일에서 `fileValidation` → `queueCreation` → `queueAudible` → `queueStart` trace, 장치 확인, `started`, **0.08초 이상 진행된 clock**, `stopped`, EOF 종료를 관찰했다. 실제 `OutputWorkerProcess` host와 build187 helper의 opt-in 테스트는 0.1초 자연 종료·3초 prefill 초과 스트리밍·정지, 루프 교체의 예약 샘플 경계·exit tail 종료까지 통과했다. AudioQueue 시계 조회 오류·2초 진행 정지는 실패로 닫는다. 이는 물리 청취나 70초 음악 스트리밍·최종 앱 GUI의 반복 루프 검증이 아니다.

build187의 실제 격리 앱에서 f0r h3r DJ Intro를 내장 스피커로 지정해 재생 시작·진행·정지를 확인했다. 섹션 루프 2회차에 진입했고 재생 중 해제는 다음 경계·잔향 재생까지 진행했지만, 마지막에 `오디오 출력 상태가 올바르지 않습니다`가 표시됐다. 장치 재검사 timer가 queue의 마지막 buffer 처리·완료 callback 사이에 실행될 수 있는 경합으로 좁혔다. build188에서는 queue 완료 표식을 별도로 읽어 이 짧은 구간의 재검사를 건너뛰었다. 같은 격리 앱 경로에서 2회차→해제→잔향 자연 종료가 오류 없이 끝났고 helper도 남지 않았다. [build188 QA](0.80-build188.md). build187의 worker/host 테스트 통과를 실제 앱 루프 성공으로 해석하지 않는다.

[Focusrite의 세대 확인 안내](https://support.focusrite.com/hc/en-gb/articles/208295789-Which-generation-of-Scarlett-do-I-have)는 본체 일련번호를 기준으로 한다. macOS가 노출한 일련번호만으로 그 기준을 적용할 수 없어 **실제 세대는 미확정**이다. - 2026-09-24 재확인: Focusrite의 [Control 2 릴리스 노트](https://support.focusrite.com/hc/en-gb/articles/13289679039378-Focusrite-Control-2-Release-Notes)는 2026-09-15판에서 **2세대 6i6**과 macOS 26을 지원 대상으로 표시한다. 이는 연결된 장치가 2세대라는 증거도, 실제 HAL 초기화 성공의 증거도 아니다. 이 기기의 정확한 세대·제어 소프트웨어·다른 앱에서의 동일 경로 동작을 별도 확인할 때까지 장치 노후화와 앱 출력 결함을 모두 미확정으로 둔다.

## 판정과 후속

현재 증거는 worker의 `outputNode` 획득 중 HAL IPC 대기를 특정한다. 내장 기본 상태에서 같은 worker가 성공한 점과, Scarlett 기본 상태를 유지한 채 명시적 내장 AudioQueue가 성공한 점도 확인했다. **시스템 기본 출력 변경은 진단에만 사용했다.** 명시적 장치의 새 backend는 renderer의 48kHz stereo PCM과 프레임 시계·루프 변경·취소를 연결했으나, 장치 분리/재연결, 실제 음악 청취와 장시간 반복은 출시 전 검증이 필요하다. Scarlett의 생성 지연과 HAL 서버 측 정확한 원인은 여전히 미확정이다. timeout을 늘리거나 UI 스레드로 장치 획득을 옮기는 변경은 근거가 없다. 기존 helper 격리·사용자 취소·정리 동작을 유지한다.

다음 재현은 같은 최종 빌드에서 **명시적 내장 출력**의 cold start·연속 Play/Stop·실제 청취·helper 정리를 확인한다. Scarlett는 세대와 호환성이 확정되지 않은 별도 진단 대상으로 유지하고, 출력 성공 자체를 0.80 필수 조건으로 삼지 않는다. Scarlett 초기화가 실패해도 앱이 멈추지 않고 오류·취소·내장 출력 재시도가 작동해야 한다. 실패한 session의 helper와 CoreAudio/장치 변경 이벤트를 함께 기록한다. 그 뒤 같은 앱에서 5–10초 MP4와 오디오/영상 프레임을 검사한다. 내장 출력 반복 재생과 실패 뒤 복구·영상 검증이 완료되기 전에는 0.80 출고를 승인하지 않는다.
