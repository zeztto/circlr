[build218 실제 앱](0.80-build218-native.md)은 작은 QA 곡 `⌘S`가 macOS `clonefileat`에서 30초 넘게 멈춰 실패했다. build219의 streaming 후보는 리뷰에서 FIFO 미디어 source를 blocking open하는 정지 위험이 발견돼 GUI 실행 전 제외했다. build220은 source를 `O_NONBLOCK|O_NOFOLLOW`로 열어 일반 파일인지 확인한 뒤 1MiB 청크로 staging에 쓰며, media checksum은 복사 완료 후 계산한다. 다른 프로세스가 저장 중 같은 media filename을 교체하는 기존 경합은 남아 있다.

집중 `CoreTests` 2개는 FIFO media의 즉시 거절과 1MiB 경계 너머 바이트 보존을 확인했다. 읽기 전용 코드 재검토는 이전 FIFO 정지 경계가 닫혔고 새 고확신 P1/P2를 발견하지 못했다. 전체 `swift test`는 **1,187개 중 14개 skip, 실패 0, 종료 코드 0**이었다. Python MCP/agent kit 소스는 변경하지 않아 이전 실행 결과를 build220 검증으로 재기록하지 않는다.

`./scripts/build-app.sh`는 build220 arm64 앱과 오디오 helper 5개를 패키징했고 `codesign --verify --deep --strict`가 통과했다. 실행 파일 SHA-256은 `424c6229a17faed5ca4eb9534b823bc1bfa3ad65c9bd23bb964d941cf03488c2`다. 기존 `PlaybackFollowCameraCurve` Sendable 경고는 남지만 컴파일 실패는 없었다.

[Documents 경로의 실제 앱 QA](0.80-build220-native.md)는 manifest 파일 선택 열기 이후 첫 `⌘S`가 30초 넘게 멈춘 **FAIL**이다. `sample`의 main thread는 `Darwin.open`을 호출한 뒤 커널 `__open`에서 대기했고 staging은 0B였다. build218의 `clonefileat` 대기와 다른 호출 위치다. 원본 demo·QA project·일반 폴더, 시스템 기본 출력은 불변이었고 격리 앱/helper는 종료했다. 보호 경로 접근 범위와 코드 문제를 분리하려고 동일 앱/곡을 `/tmp`에 복사한 통제 native 시험을 별도 수행한다. 해당 결과 전에는 원인을 단정하지 않는다.

[동일 빌드 통제 시험](0.80-build220-temp-native.md)에서 byte-identical 앱·곡을 `/tmp`에 놓고 manifest 파일을 선택하자 `⌘S`는 약 0.7초에 완료됐다. 원래 Documents QA 경로에서 `.circlr` 폴더 자체를 선택했을 때도 약 0.6초에 완료됐다. 두 성공 사례의 미디어 6/6 hash와 기본 출력은 유지됐다. 이는 **선택한 manifest 한 파일과 패키지 폴더의 macOS 접근 범위 차이**가 정지와 연관된다는 강한 증거지만, TCC 내부 상태를 직접 확인한 것은 아니므로 시스템 원인을 확정하지 않는다. build221 GUI는 manifest 선택 뒤 같은 폴더를 다시 선택해 미디어 접근을 확보하도록 한다.

Scarlett 6i6의 세대는 미확인이다. 해당 장치의 정상 입출력은 이 빌드의 성공 근거가 아니며, 시스템 기본 장치는 native QA에서도 변경하지 않는다.
