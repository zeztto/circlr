# 0.80 최종 후보 외부 Codex→MCP 모델 E2E 실행 준비

```text
TEMPLATE_VERSION: qa-response-v1
STATUS: EXECUTED_ONCE — build239 결과는 0.80-build239-model-native.md 참조
SCOPE: signed isolated final 0.80 QA app; one Codex CLI model turn; pinned bundled MCP; one MIDI step
OWNER: qa/run-0.80-model-e2e.py
```

build230의 [실제 모델 QA](0.80-qa232-model-native.md)는 0.80 후보의 이전 바이너리 결과다. 이 준비 절차는 이후 [build239 실제 모델 QA](0.80-build239-model-native.md)에 한 번 실행됐다. [최종 gate](0.80-ai-agent-journey.md)의 토큰 과다 문제를 줄이기 위해 모델은 `circlr_context → 대상 circlr_inspect → circlr_apply` 한 번만 수행했다. 독립 QA client가 정확한 note 변화, 다른 MIDI lane 불변, Undo 원복, 같은 한 step 재적용, 저장·재열기, nonzero 48 kHz/stereo/24-bit WAV를 검사했다. 재적용 이후 단계는 **모델 수행이 아닌 QA 수행**으로 보고한다. 아래의 제한 환경과 gateway는 그 실행 **이후** 하네스에 추가됐다. 기존 build239 모델 turn이 이 새 경로를 통과했다고 주장하지 않는다.

`qa/run-0.80-model-e2e.py`는 이미 생성·서명·실행 중인 고유 QA bundle 및 앱 안에 열린 저장된 `.circlr` 사본을 요구한다. 앱 실행과 fixture 작성은 별도 native QA 담당이며, 하네스 자체는 설치 앱·사용자 프로젝트·시스템 오디오 기본값을 열거나 변경하지 않는다. 증거 폴더는 Git-ignored `qa/generated/r80-model-*`로 새로 지정한다. 모델 전에는 QA `selected.json`의 동일 사용자·0600 권한, socket inode, bundle/build/runID와 실제 `circlr_snapshot.runtime` 및 fixture path/revision을 대조한다. QA 앱에 동봉된 kit를 전용 client에 설치하고 전체 managed file hash를 확인한다. private `/tmp/cq80.*`를 **Codex CLI와 MCP gateway의 HOME**으로 사용하며, 그 HOME의 Agent symlink는 QA Agent만 가리킨다. `CIRCLR_SOCKET`과 `--socket` 직결은 사용하지 않는다.

이 스크립트는 **내부의 신뢰된 QA 담당자만 수동 실행**한다. QA 앱·프로젝트·bundle ID를 실제 값으로 설정한 뒤 순서대로 실행한다. `--evidence`는 실행마다 새로운 경로여야 한다. fixture 절대 경로와 projectID가 같다면 앱 재시작으로 runID가 달라져도 `model` 재호출을 막는 0600 독점 marker가 `qa/generated/`에 남는다. 중간 실패 시 같은 fixture로 재시도하지 말고 당시 앱 상태와 trace부터 보존한다.

```sh
QA_APP='/absolute/path/to/signed-final-r80-qa.app'
QA_ROOT="$HOME/Library/Application Support/circlr-r80model-qa"
QA_PROJECT="$QA_ROOT/fixtures/model-r80.circlr"
QA_BUNDLE='com.circlr.r80modelqa'
QA_BUILD="$(/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' "$QA_APP/Contents/Info.plist")"
QA_EVIDENCE='qa/generated/r80-model-final'
python3 qa/run-0.80-model-e2e.py prepare --app "$QA_APP" --qa-root "$QA_ROOT" --project "$QA_PROJECT" --bundle-id "$QA_BUNDLE" --build "$QA_BUILD" --evidence "$QA_EVIDENCE"
python3 qa/run-0.80-model-e2e.py model --app "$QA_APP" --qa-root "$QA_ROOT" --project "$QA_PROJECT" --bundle-id "$QA_BUNDLE" --build "$QA_BUILD" --evidence "$QA_EVIDENCE"
python3 qa/run-0.80-model-e2e.py verify --app "$QA_APP" --qa-root "$QA_ROOT" --project "$QA_PROJECT" --bundle-id "$QA_BUNDLE" --build "$QA_BUILD" --evidence "$QA_EVIDENCE"
```

현재 `model`은 fixture 단위 marker와 `model-started.json`을 생성한 뒤 `codex exec --json --ephemeral --ignore-user-config --sandbox read-only`를 최대 한 번 실행한다. `--approve-for-me`와 writable `--add-dir`는 사용하지 않는다. subprocess 환경은 private `HOME`, 실제 계정 인증에 필요한 `CODEX_HOME`, 제한된 `PATH`·locale·임시 경로 등만 전달하며 API key·SSH socket·`CIRCLR_SOCKET` 환경 변수는 상속하지 않는다. 전역 Codex config/login을 수정하지 않는다. 앱 동봉 MCP adapter 앞의 QA gateway는 모델에 `context`·대상 `inspect`·계획된 `apply`만 노출하고, 읽기 완료 뒤 `apply` 한 건을 전달하기 직전에 bundle/build/runID, socket inode, fixture path, project/revision/layout와 저장 manifest hash를 다시 확인한다. 대상 변경·승인 거절·timeout·응답 유실 때 같은 fixture의 write를 재시도하지 않는다. 먼저 QA 앱 snapshot, manifest, 원시 trace로 불확실성을 조사한다.

이 검사는 **production용 보안 경계나 fixture 전용 write 보장이 아니다**. Codex 인증을 유지하려면 실제 `CODEX_HOME`을 모델 프로세스에 제공해야 하며, read-only shell에서도 그 경로의 인증·설정 파일을 읽을 가능성을 하네스가 원천 차단하지 못한다. `read-only` sandbox와 사후 trace 검사는 사전 정보 유출 방지 수단이 아니다. gateway의 prewrite snapshot과 실제 `apply` RPC는 원자적이지 않으므로, 그 사이 동일 projectID/revision을 유지한 채 문서 경로가 바뀌는 경쟁 상태까지 막지는 못한다. adapter와 앱의 runID·socket identity·project revision 검증이 별도로 동작하지만 이 한계를 없애지는 않는다. 원시 trace와 stderr는 ignored evidence에 남기되 외부 공유 전 민감정보를 검사한다. 현재 제한 환경에서의 계정 상태 조회와 하네스 unit test는 통과했으나, 새 gateway 경로의 **실제 모델 write·approval 동작은 미검증**이다. 기존 build239 결과를 그 증거로 사용하지 않는다.

`verify`는 trace의 모든 MCP/shell 호출 수명주기를 검사하고, 완료된 context·inspect 뒤 시작한 `circlr_apply`가 **정확히 한 건**인지, 예상 project/revision/operation과 결과 revision 증가가 맞는지 확인한다. 추가·미완료 MCP write, 예외 외 shell 명령과 file change는 실패로 처리한다. 기존 build239 실행의 trace만 새 검증기로 소급 PASS했으며, 새 설치 kit 전체 해시 gate는 당시 plan에 없어서 소급 인증하지 않는다. 앱 활동 기록의 `실행 · apply` 행도 읽어 `model-activity.json`에 남긴다. 그러나 이 API 기록만으로 **화면 콘솔 가시성**을 증명할 수 없으므로, 같은 runID의 native 앱에서 AX 또는 스크린샷으로 해당 행을 별도 확인해야 R80-15를 닫는다. `report.json`의 `AUTOMATED_PASS`는 그 기계적 범위만 뜻하며 `consolePixelOrAX`는 `PENDING`으로 남는다. 실제 청취·물리 마이크·앱 내 계정 대화·trusted STOP의 증거도 아니다.

각 단계가 중간에 실패하면 `report.json`을 작성하지 않는다. 특히 `verify`가 Undo·재적용 이후 실패했다면 fixture는 수정되었을 수 있으므로 현재 snapshot/manifest/소켓 상태를 먼저 보존하고 새 QA app/fixture/evidence로 원인 수정 뒤 재현해야 한다. 검사 완료 후 QA 앱/helper/socket 잔류, 원본 앱·demo/kit byte identity와 시스템 기본 입출력 불변을 별도로 확인한다. 짧은 fake HOME은 QA evidence의 `fake-home-path.json`이 가리키는 **정확한 경로**만 수동 회수한다.
