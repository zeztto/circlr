# 0.80 build230 녹음 입력·문서 전환 감사 (2026-09-24)

## 범위와 판정

`release/0.80.0`의 `24e3aad`를 소스만 읽었다. 앱·입력 장치·시스템 오디오 설정을 실행하거나 변경하지 않았고 실제 마이크 take의 성공/실패를 재현한 결과가 아니다. 기존 [선택 입력 조사](0.80-selected-input-investigation.md)의 CalDigit `AVCaptureSession.startRunning()` 및 직접 `AudioDeviceCreateIOProcID` 10초 지연은 그대로 미해결이다. Scarlett이 구형이라는 사실만으로 모든 입력 실패의 원인을 Scarlett로 돌릴 수 없다.

**다음 소프트웨어 수정의 우선순위는 녹음 중 문서 전환 차단이다.** `AudioRecorder.stop`은 비동기 파일 마무리를 시작하고 바로 반환한다 (`Sources/CirclrAudio/AudioRecorder.swift:111-123`). 그러나 다음 경로는 `stop()` 직후 프로젝트를 교체하거나, 비동기 데모 로드가 완료될 때 `stop()` 후 바로 교체한다.

| 전환 경로 | 소스 위치 | 현재 경계 |
| --- | --- | --- |
| 새 프로젝트 / 기존 프로젝트 열기 | `Sources/CirclrApp/AppStore.swift:912,914-945` | `retireDemoCopy(); stop(); project=...`가 녹음 파일 마무리를 기다리지 않음 |
| 새 곡·템플릿 | `Sources/CirclrApp/StartupWorkspace.swift:16-29` | `stop(); project=fresh`가 같은 문제 |
| 동봉 데모 | `Sources/CirclrApp/BundledDemo.swift:59-89` | 시작 시와 비동기 적용 직전 모두 녹음 `busy` 검사가 없음 |

`stop()`은 녹음 중 `stopRecording()`을 호출하지만 대기하지 않는다 (`Sources/CirclrApp/AppStore.swift:741`). `finishAudioRecording()`은 기존 프로젝트 ID·서클·트랙을 잡고 `recorder.stop` 완료 callback에서 **그때의** `self.project`에 take를 저장한다 (`Sources/CirclrApp/AppStore.swift:1135-1149`). `AudioTakeEditing.save`는 프로젝트 ID가 다르면 의도적으로 거부한다 (`Sources/CirclrCore/AudioTakeEditing.swift:4-9`). 따라서 위 전환이 녹음 중 허용되면 원래 문서에 take가 붙지 않고 파일 복구 링크로만 남을 수 있다. 현재 recovery 파일 보존은 유용하지만 정상적인 DAW 녹음·저장 동선의 대체물이 아니다. 이 연결은 소스에서 확인되는 경쟁 조건이며 물리 장치 재현 판정은 아니다.

반대로 MCP `open`은 `AgentWorkspace.swift:254-255`의 공통 `!audioRecordingBusy` guard를 거쳐 `beginAgentOpen`에 들어가므로 동일 결함으로 단정하지 않는다. 앱 종료는 `CirclrApp.swift:66-82`에서 최대 10초 기다리고, 정리되지 않으면 종료를 취소한다. UI 문서 전환에 그에 상응하는 경계가 빠진 것이다. `AppStore.save(as:)` (`AppStore.swift:827-843`)도 녹음 중 take가 아직 프로젝트에 추가되지 않은 상태에서 저장 완료로 표시할 수 있어, 전환 차단과 함께 저장 의미를 명확히 해야 한다.

## 권장 수정 계약

1. 모든 문서 교체 진입점에서 `audioRecordingBusy || midiRecording`이면 교체·`confirmDiscard`·`retireDemoCopy` 전에 거부하고, 사용자에게 녹음 정지와 **파일 마무리 완료 후** 다시 실행하도록 알린다. 녹음을 암묵적으로 정지하고 곧바로 문서를 바꾸지 않는다. 기존 `stop()`은 유지하되 전환 준비 수단으로 쓰지 않는다.
2. 비동기 데모 로드에서는 시작 때뿐 아니라 worker 결과 적용 직전에 같은 gate를 다시 확인한다. 그 사이에 녹음을 시작했다면 로드 결과를 적용하지 않고 복사본 lease를 안전하게 정리한다. 기존 프로젝트·take·recovery URL은 유지한다.
3. `save(as:)`는 녹음 진행·마무리 중에는 “현재 take가 저장된 프로젝트”로 오인되지 않도록 막거나, 명시적으로 파일 마무리 완료 뒤 저장한다. 단순한 프로젝트 snapshot 저장만으로 녹음 take까지 저장됐다고 표시하지 않는다.
4. 장치 없는 회귀: 지연/실패/성공 fake backend로 `starting`, `recording`, `finishing`, `cancelling` 동안 각 문서 전환의 project ID·dirty·take/recovery 상태가 변하지 않음을 확인한다. stop 완료 후 정상 take가 **원래** 프로젝트에 삽입되고, 그 다음 전환만 진행됨을 확인한다. 비동기 데모 worker 완료 시점의 재검사도 포함한다. 기존 `AudioRecorderTests.swift:44-79`는 recorder lifecycle만, `RecordingRoundTripTests.swift:48-100`은 통제된 PCM→take→저장→재생만 검사하므로 이 앱 통합 경쟁 조건을 덮지 않는다.

## 별도 미해결 입력 gate

- 기본 입력은 `AVAudioEngine.inputNode`이고 선택 UID backend는 `selectedCaptureUnavailable`로 닫혀 있다 (`Sources/CirclrAudio/AudioRecorder.swift:66-70,126-162`). 앱 UI도 기본 입력의 첫 두 채널이라고 안내한다 (`Sources/CirclrApp/RecordingWorkspace.swift:21-27`). 따라서 이 빌드에서 **선택 입력 장치로 녹음 가능**하다고 표시하지 않는다.
- `AudioRecorder.start` 10초 timeout은 UI callback을 실패로 돌리고 `CaptureAttempt.finish`를 같은 serial queue에 쌓는다 (`AudioRecorder.swift:23-44,75-109`). HAL 동기 호출이 영원히 반환하지 않으면 `busy`도 유지되어 재시도를 막는다. 이는 안전한 실패 방어이지만 bounded cleanup/같은 프로세스 복구의 증거가 아니다. 별도 입력이 정상 응답하는 호스트에서 source UID·실제 callback PCM·stop 후 resource 정리·동일 앱 재시도를 검증한 뒤에만 선택 입력 backend를 제품에 연결한다. 불응 장치에는 프로세스 경계 같은 종료 가능한 capture 설계가 필요하다.
- 최종 DAW gate는 실제 권한 있는 앱에서 녹음 시작→nonzero PCM→정지→원래 서클 take→프로젝트 저장·재열기→오디오 바운스·청취이다. 현재의 통제된 callback PCM 테스트와 CalDigit spike는 이 전체 동선을 입증하지 않는다. 구형 Scarlett의 정상 동작은 필수 성공 조건으로 삼지 않는다.
