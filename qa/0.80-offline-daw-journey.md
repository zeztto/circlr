# 0.80 build185 · 오프라인 DAW 제작 경로

상태: **범위를 한정한 native QA 통과 / 0.80 릴리스 승인 아님** · 2026-09-23. `com.circlr.integrationqa` build185 앱과 QA Application Support 안의 새 Bach Invention 8 사본 `r80-offline-build185-bach.circlr`만 사용했다. 사용자 설치 앱·프로젝트, 시스템 출력 설정, 번들 데모 원본은 변경하지 않았다. 앱을 완전히 종료한 뒤 새 프로세스에서 사본을 다시 열어 최종 저장 상태를 확인하고 QA 앱을 종료했다.

## 검증 경로

1. 번들 Bach 원본을 QA 사본으로 복사했다. 번들 원본과 복사 직후 사본의 `manifest.json` SHA-256은 모두 `a0350b4802b192bf3d7ba207a9a031f166c0c5092e60faf0f82f766da3257c34`였다. 다음 기존 harness를 build185에 실행했다.

   ```sh
   python3 qa/verify-agent-journey.py \
     --project "$HOME/Library/Application Support/circlr-integration-qa/fixtures/r80-offline-build185-bach.circlr" \
     --evidence qa/generated/r80-offline-build185-bach --build 185
   ```

   실제 MCP 27개 tool catalog와 bundle/build를 확인하고, 첫 MIDI lane에 pitch 95 step을 추가했다. 노트 76→77, 오래된 revision 거절, Undo로 원래 노트 배열 복원, 다시 적용, 저장·재열기를 통과했다. 70초 master WAV는 48 kHz/stereo/24-bit, 3,360,000 frames, nonzero PCM이며 SHA-256 `bbff5de94588bc2a877038115ce13c9451e4ecad2a37199aba8c834a9d9f849e`다. 첫 트랙의 track bounce가 오디오 서클을 만들고 저장 후 revision은 4였다. 이 단계의 상세 수치는 Git 제외 `qa/generated/r80-offline-build185-bach/report.json`에 있다.

2. 같은 QA 사본의 **두 번째 synth 트랙** 첫 section/use에서 `add_effect`로 gain effect(0.65)를 악기 출력과 트랙 출력 사이에 삽입했다. 이어 새 effect node의 `gain` automation을 설정했다. 활성 노트가 beat 3.5부터 시작하므로 실제 비교 곡선은 beat 0에서 0.2, beat 24에서 0.5이다. effect와 automation을 저장·재열기 한 뒤 node/points를 다시 inspect했다. 각 단계는 새 절대 경로에 master WAV를 내보내고 전체 PCM을 비교했다.

3. 두 번째 트랙도 `circlr_bounce`했다. 18초·48 kHz/stereo/24-bit의 nonzero asset과 오디오 clip이 생겼고, 바운스 전후 70초 master WAV의 sample 차이는 최대 **1 LSB**, RMS 차이는 **0.146 LSB**였다. 이는 이 fixture의 정량 비교이며 모든 플러그인·sidechain 조합의 null 보증은 아니다.

4. 새 오디오 clip에 `edit_audio fade`를 적용했다. 5초 fade-in과 3초 fade-out은 master PCM을 바꿨다. 저장 후 앱을 종료·재시작하고 같은 QA 프로젝트를 열었을 때 project ID, revision 10, dirty=false, clip ID와 두 fade 값이 유지됐다. 최종 사본 `manifest.json` SHA-256은 `07bb7fb038f944c3033ddf68ede116165ac6a88eed44cb19571b6ee2d5e38d86`이다. 번들 원본 manifest hash는 끝까지 불변이었다.

| master 단계 | revision | SHA-256 | 비교 대상과 최대 sample 차이 |
|---|---:|---|---:|
| 첫 bounce 뒤, FX 전 | 4 | `306580a6bc47e4d9032ba65780adfbef8eee2f99a5c3bc0640b9e2c2ec85d2b1` | 기준 |

모든 표의 WAV는 70초·48 kHz/stereo/24-bit, nonzero PCM이다. 바운스 asset도 18초·nonzero이며 SHA-256은 `20f546b5cc5b8bb297ec486c73d22c1b5d06b291532a33d32d3f2c43669b77bb`다. 각 파일의 hash, peak, RMS, frames, job ID, clip/asset/node ID와 저장 revision은 [기계 판독 증거](evidence/r80-offline-daw-build185.json)에 있다. 결과 파일은 `~/Library/Application Support/circlr-integration-qa/fixtures/` 및 `Bounces/`에 남겨 두었으며 Git에는 오디오를 추가하지 않았다. 최종 증거 작성 시 7개 master WAV와 바운스 asset의 SHA-256을 다시 계산했다.

### 시험 설계상 무음 구간

초기 gain automation은 beat 0에서 0.2→beat 2에서 1.0이었다. 두 번째 트랙 첫 노트가 beat 3.5이므로 FX-only와 그 automation WAV가 byte-identical인 것은 정상이다. 바운스 asset 처음·끝 0.7초의 PCM peak도 각각 0이어서 0.7초 fade 시험 역시 WAV가 동일했다. 두 경우 모두 실제 신호가 있는 구간으로 범위를 옮겨 위의 차이를 확인했다. 동일 WAV만을 근거로 automation/fade 결함을 선언하지 않는다.

## 판정 경계

이 검증은 **MCP가 실제 앱에 적용한 MIDI→FX→automation→master WAV→트랙 bounce→오디오 fade→저장·앱 재시작 경로**를 입증한다. 오디오 입출력 장치에서의 실제 재생·청취, 마이크 녹음, GUI의 FX/automation/fade 조작, 전체 stem 폴더 export, AU 플러그인 호환성, 음악적 품질은 검증하지 않았다. track bounce는 section track의 오디오 asset이지 전체 곡 stems export와 동의어가 아니다. build185의 `AVAudioEngine.outputNode` timeout은 [출력 조사](0.80-output-investigation.md)에 남아 있어 **릴리스 gate는 열린 상태**다.
