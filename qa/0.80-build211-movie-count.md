# 0.80.0 build 211 후보 — MP4 마지막 프레임 집계

2026-09-24 KST. build 210의 실제 앱 녹화 `qa/generated/r80-build210-native-movie/build210-native-37s.mp4` (SHA-256 `7a81a82facda9e1a0090fa2f4d15b1a581feba036efb3cac7b327f0bb4b50504`)는 UI 저장 문구 1,118프레임, AVFoundation pixel decoder 1,117프레임이었다. MP4 길이는 37.29875초, 마지막 decoded PTS는 37.265초로 차이가 33.75ms다. 같은 build 210의 짧은 7.43827초 녹화는 UI와 decoder가 223프레임으로 일치했다. 긴 녹화 중 snapshot의 `view.loopMode`는 `off`이므로 scheduled loop exit로 단정할 근거는 없다.

build 210의 `CanvasMovieWriter`는 영상 PTS가 유한한 PCM 종료 시각 **이전**이면 encoder에 보냈지만, `finish()`에서 MP4 session을 PCM 종료 시각에 잘랐다. 48,020 audio frames(1.0004167초)의 PCM과 0~1초의 31개 캡처를 인코딩하면 writer는 31개를 세지만 MP4 pixel decoder는 30개만 출력한다. 1초 PCM의 정확한 종료점 1.0초에서도 동일한 31/30 차이가 재현된다. 실제 37초 녹화의 마지막 입력 PTS는 기록되지 않았으므로, 원본 MP4만으로 사라진 입력 프레임의 정확한 시각을 확정할 수는 없다.

초기 build 211 후보의 `time + 1/30 <= audioEnd` guard는 1초 PCM의 0.98초 **유효 프레임**까지 버리는 문제가 있어 폐기했다. 최종 후보는 마지막 수용 영상 PTS 뒤 최대 1/30초를 MP4 session에 허용한다. PCM 제출은 실제 오디오 종료 시각에 그대로 멈춘다. 유한한 PCM에 대한 session 연장은 최대 1/30초이며, 실제 backpressure·타임스탬프 충돌의 `droppedFrames` 집계도 유지한다.

1초 PCM의 정확한 종료점과 1.0004167초 PCM의 근접 종료점에서 각각 큐 수용·저장·독립 decode **31/31/31**, 누락 0이다. 두 MP4의 영상 길이는 1.033333초, PCM readback은 각각 1.0초·1.0004167초다. 1초 PCM에서 PTS 0.98초 유효 프레임도 보존·decode되며 영상과 PCM readback 길이는 모두 1.0초다. Scheduled loop exit 종료점 역시 31/31/31, 영상 1.033333초/PCM 1.0초다.

검증: `swift test --filter CanvasMovieWriterTests` — 11개 통과, `git diff --check` 통과. 후속 [build211 실제 앱 native QA](0.80-build211-native-movie.md)의 38.006667초 MP4에서는 UI/독립 decoder 1,138/1,138프레임이 일치했다. build210의 1,118/1,117 불일치는 역사적 실패 기록으로 유지한다. 한 번의 유사 길이 수동 종료만으로 모든 종료 조건을 보증하지 않는다.
