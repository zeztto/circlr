# 0.80 build185 · 정밀 편집과 작업별 취소

상태: **부분 통과 / 릴리스 승인 아님** · 2026-09-23. 테스트 대상은 `release/0.80.0`의 0.80.0/build185를 복사·재서명한 `com.circlr.integrationqa` 앱이다. 원본 앱의 `codesign --verify --deep --strict`가 통과했고 격리 앱 SHA-256은 `18f6f066c0e1668f8dfb597896e0a5655ef3ce42c5764c9c7838064fcdaec621`이다. 검증은 QA Application Support의 별도 데모 사본만 사용했다.

## 자동 검사

- 최종 코드의 전체 Swift 테스트 **1011개 실행·3개 skip·실패0**: [로그](generated/r80-build185-swift-tests-final.log). 이전 중간 코드의 1010개 통과 결과는 이 최종 결과로 대체한다.
- MCP adapter 회귀: [39개 통과 로그](generated/r80-build185-mcp-tests.log). `cancel_job`은 projectID/jobID를 요구하고 음악 revision은 요구하지 않으며 read-only와 capability 없는 앱에서 거절한다.
- 격리 QA 취소 검증 스크립트: [4개 테스트 통과 로그](generated/r80-build185-agent-cancel-harness-tests.log). 사용자 앱 socket·기존 증거 경로를 거절하고, 작업 완료/늦은 staging WAV를 성공으로 오인하지 않는다.

같은 앱에 동봉된 worker의 기본 출력/내장 스피커 지정 **무음 probe 두 건**도 출력 노드 획득에서 각각 12초 timeout이었고, circlr 외부의 최소 `AVAudioEngine.outputNode` 접근 역시 12초 timeout이었다. 원인은 미확정이며 실제 음악 재생 PASS로 해석하지 않는다. [재현 경계와 원자료](0.80-output-investigation.md).

별도 Bach QA 사본에서는 **실제 UI MIDI 편집→Undo→Redo→저장→앱 종료→새 프로세스에서 재열기**를 끝까지 확인했다. 첫 lane의 고정 note ID `0167053F-23A0-5A1B-85E8-F6C9D4FAC6F2`에서 velocity 127→100, revision 0→1을 UI와 MCP inspect로 대조했다. ⌘Z 뒤 127/revision2, ⇧⌘Z 뒤 100/revision3, ⌘S 뒤 dirty=false였다. 앱을 종료·다시 실행해 저장한 QA 사본을 열자 같은 note ID·beat0.5·pitch65·velocity100, 전체 76개 노트, revision3·dirty=false가 유지됐다. [재열기 결과](evidence/r80-build185-ui-midi-persistence.json). 동봉 Bach 원본 manifest SHA-256 `a0350b4802b192bf3d7ba207a9a031f166c0c5092e60faf0f82f766da3257c34`는 불변이다. 이는 **정지 상태의 MIDI GUI 동선**이며 재생 중 편집이나 오디오 take/FX/stems의 완료 증거가 아니다.

이 결과는 **에이전트 job 취소**이지 AI 세션의 후속 MCP 쓰기 권한 철회가 아니다. `circlr_stop`의 DAW 전체 정지와 구분한다. build185를 사용자 설치 앱으로 교체하거나 태그·GitHub Release로 게시하지 않았다.

## 한 번에 모아 검수할 항목

출력 timeout 원인을 좁히고 동일한 최종 후보에서 자동 QA를 다시 마친 뒤, 사용자가 앱을 직접 사용할 수 있을 때 한 세션으로 확인한다. ① 내장 출력과 Scarlett에서 곡·섹션 루프가 실제로 들리는지와 중단/재시작 뒤 잔음, ② MIDI·오디오 편집기를 열고 재생하면서 노트/클립 수정·Undo·저장, ③ 저장한 MP4의 처음·중간·끝 화면과 소리·신호 흐름, ④ f0r h3r의 음악적 완성도다. 이 청취·감상 평가는 현재 PASS로 기록하지 않는다.
