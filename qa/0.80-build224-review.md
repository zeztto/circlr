# build224 세로 송폼 라벨 코드 리뷰

범위: `Sources/CirclrApp/CanvasPresentation.swift`와 `Sources/CirclrCore/CanvasLabelLayout.swift`의 build224 변경만 읽기 전용 검토했다. 제품 소스는 변경하지 않았다. 대상 테스트 및 전체 빌드는 부모 작업에서 실행 중이므로 중복 실행하지 않았다.

## 판정

현재 diff에서 확정할 수 있는 P1/P2 논리 결함은 찾지 못했다. `CanvasPresentation.swift:233-234`는 `workspaceViewport.width < 900`인 곡 뷰의 직접 섹션에만 일반 라벨의 viewport 조정을 새로 허용한다. 선택·hover·재생 중 active 섹션의 기존 우선순위는 그대로다. `CanvasLabelLayout.swift:52-78`는 기존 가까운 후보와 가장자리 후보 뒤에 lattice를 두므로 기존에 배치되던 라벨 위치를 먼저 유지한다. 모든 후보는 작업 viewport 안에 있어야 하고 다른 라벨·편집 도구·다른 원과 충돌하지 않아야 한다. 원 중심 또는 원의 일부가 작업 viewport에 닿지 않으면 조정 후보를 만들지 않는다. `CanvasPresentation.swift:220`의 상위 필터도 일반 직접 섹션의 화면 밖 중심을 새로 요청하지 않는다.

## 재생 프레임 비용

`drawReadableLabels()`는 재생 중에도 프레임마다 호출된다. 새 lattice 25점의 생성·정렬은 허용된 각 라벨에 대해 가까운 후보가 이미 성공할 때도 일어난다. 정확한 `CanvasLabelLayout.swift`를 `swiftc -O`로 별도 컴파일한 밀집 synthetic 배치의 호출 시간은 7개 라벨에서 build224 **0.016ms** 대 이전 **0.008ms**, 100개에서 **0.87ms** 대 **0.56ms**, 200개에서 **3.62ms** 대 **2.50ms**였다. 각 수치는 반복 호출 평균이며 SwiftUI/AppKit 텍스트 그리기·실제 scene 탐색을 제외한다. 일반 7섹션 곡에는 작은 증가지만, 매우 긴 송폼이나 앨범의 대형 장면은 실제 재생 FPS와 frame-gap 진단으로 확인해야 한다. 이 synthetic 수치만으로 성능 P2를 확정하지 않는다.

## native 판정에 남긴 사항

- build223의 720×900 화면은 직접 섹션 원 7개가 남아도 04/06/07 이름표가 빠졌다. 새 lattice가 그 **실제 장면에서 7/7 라벨**을 확보하는지는 build224 전체 창 캡처로 확인해야 한다. 기존 `CanvasLabelLayoutTests`는 원/도구 충돌과 결정성·우선순위를 검증하지만 이 7섹션 장면 자체를 고정하지 않는다.
- 마지막 후보는 viewport의 먼 빈 곳까지 검색하므로 섹션과 라벨 사이 leader 선이 길어질 수 있다. 픽셀 검수에서는 라벨이 실제 섹션과 명확히 연결되는지, leader가 다른 원·텍스트를 지나 읽기 어렵게 만들지 않는지 확인한다. 원·라벨 배치 충돌 검사는 leader 선과의 교차까지 검사하지 않는다.
- 선택 상태의 라벨은 이미 viewport 조정이 가능했으며 이번 lattice도 함께 사용한다. 실제 창에서는 섹션 선택, 재생 팔로우, 콘솔 40/122/180pt, 감상 모드 왕복에서 배치가 급격히 점프하거나 주요 레이블을 밀어내는지 확인한다.

`git diff --check` 통과. 위 native 및 프레임 성능 경계는 완료를 주장하는 근거가 아니라 후속 QA 관찰 항목이다.
