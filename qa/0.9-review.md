# 0.9 · 에이전트 연결과 음악 제작 검증

환경: Apple Silicon Mac, macOS 26.5.1, SwiftPM Release. `com.circlr.hierarchyqa` 검증 앱과 별도 Application Support 저장소를 사용했다. 실행 중인 production 앱과 사용자 곡·복구본은 검증 대상으로 사용하지 않았다.

## 자동 검증

- Swift 70/70 통과: 기존 61개 회귀와 MIDI 생성/SMF/호환 decode, synth·sampler PCM, 이펙트/잔향/output gain을 포함한 bounce 동등성·복원, 원자적 agent edit·stale revision·note 입력 검증을 포함한다.
- Python MCP 3/3 통과: 실제 stdio handshake·14개 tool catalog, bool revision/NaN/범위 초과/잘못된 operation 거부, 정상 note 입력을 확인한다.
- 로그: `generated/0.9-tests-final.log`, `generated/0.9-mcp-python-tests.log`, `generated/0.9-release-final-build.log`.

## 실행 중인 앱과 실제 MCP

`mcp/native_smoke.py --require-minimized`는 MCP stdio를 시작하고 실제 QA 앱 socket과 통신한다. 음악 엔진을 대체한 응답 fixture를 사용하지 않는다. 매 실행 새 폴더에 원본 f0r h3r의 QA 사본을 만들며 기존 결과를 덮어쓰지 않는다.

`generated/0.9-final/0.9-mcp-native.json`에 다음 성공 증거가 있다.

1. MCP initialize와 14개 도구 탐색, snapshot의 실제 앨범·asset·track 식별.
2. MCP로 창 최소화 → 실제 프로젝트 비동기 열기. 시작과 끝 runtime의 `minimized: true`.
3. Chorus lead에 arpeggio 64 notes 생성, 이전 revision으로 쓰기 거부, Undo로 기존 notes 정확히 복원.
4. rename과 잘못된 node edit를 섞은 batch가 변경 없이 거부됨.
5. 동일 native request bytes 재전송은 한 번만 적용. 동일 ID의 다른 payload는 거부됨.
6. export 즉시 stop → cancelled. 새 export 도중 문서 편집 → stale_revision failed. 두 경로 모두 결과 WAV가 존재하지 않음.
7. 원본 master export → lead track bounce → 바운스 후 master export → 미디어 포함 프로젝트 save. 모든 job completed, dirty false.

작업의 명령 처리·바운스·WAV 생성·저장에는 화면 조작을 쓰지 않았다. 화면 도구는 앱 실행과 이후 표시 검토에 사용했다. MCP client의 설치·등록은 별도이며 `.mcp.json` 작성이 현재 대화의 도구 목록 자동 갱신을 뜻하지 않는다.

## 오디오

실제 f0r h3r은 116 BPM, F♯ minor, 48마디, 8트랙, 2,728개 MIDI notes다. 출력은 48 kHz stereo/24-bit, 101.310354초다. Splice 보유 샘플 6개를 사용하고 0 credits를 지출했다. 파일명과 SHA-256은 `music/f0r-h3r/v1/production-report.json`에 있다.

원본과 바운스 후 WAV의 stereo interleaved sample 9,725,794개를 비교했다. 최대 차이는 **24-bit PCM 1단계**, RMS 차이는 약 2.1563e−8이다. 분석기는 `qa/analyze-bounce.py`, 결과는 `generated/0.9-final/bounce-audio-comparison.json`에 있다. 본편 WAV의 peak는 0.8709636, clipping samples는 0이다. 실제 PCM 렌더·수치 검증이며 주관적 청음을 완료했다는 주장은 하지 않는다.

## Native UI

- 실제 바운스 파형·원본 복원·clip 시작/길이/볼륨/tempo 설정과 하단 콘솔이 동시에 보이는 화면을 확인했다. 콘솔이 편집 컨트롤을 가리던 높이를 조정했다.
- 콘솔 `state`는 현재 제목/r7/8트랙/8섹션을 표시했다. UI 원본 복원으로 r8, 콘솔 Undo로 r9와 원본 복원 버튼을 되살리고 콘솔 save를 완료했다.
- Esc로 콘솔을 접고 Ctrl+`로 다시 펼쳤다. 다시 열면 로그의 처음으로 돌아가는 문제를 발견해 최신 로그로 이동하도록 수정했다.
- 타임스탬프 줄바꿈을 없앴다. 로그 위 휠은 로그를 스크롤하고 캔버스 위 일반 휠은 기존 zoom으로 전달한다.
- 화면 증거: `generated/0.9-console-bounce.png`, 최종 실행 파일의 `generated/0.9-final-console.png`와 `generated/0.9-final-console-ax.txt`.

최종 휠 검증에서 로그 scrollbar는 0.9574468 → 0.4382979로 이동하고 캔버스 zoom은 201.7962963으로 유지됐다. SwiftUI overlay의 실제 bounds를 전달하고 AppKit monitor/scrollWheel 양쪽에서 처리했다. `generated/0.9-console-scroll-evidence.json`에 MCP snapshot 비교를 기록했다. 최종 실행 파일에서 MCP 전체 시나리오와 Swift 70개 테스트도 다시 통과했다.

## 발견과 수정

처음 최소화 상태에서 open을 실행했을 때 새 ad-hoc 앱 서명에 대한 macOS Documents 권한 요청이 나타났다. sample에서 main thread가 ProjectStore.load의 파일 open syscall을 기다리는 것을 확인했다. 사용자가 시스템 권한을 허용했으며 해당 시도는 성공 검증으로 계산하지 않았다.

이 문제를 계기로 MCP open을 별도 worker의 비동기 job으로 바꿨다. request ID와 generation으로 취소·문서 변경 이후 지연 결과를 막는다. 시스템 권한을 우회하거나 TCC 설정을 수정하지 않았다. 이후 최종 MCP 전체 흐름은 최소화 상태에서 성공했다. 진단은 `generated/0.9-minimized-sample.txt`와 `generated/0.9-file-access-log.txt`에 보관한다.

코드 검토에서는 socket 소유자·권한·입력 크기·peer UID, shell/TCP 미노출, revision guard, batch 원자성, 파일 덮어쓰기 경계, 완료 후 generation 확인을 대조했다. 최근 job을 임의 순서로 제거하던 코드를 FIFO로 수정했고 렌더 진행률의 역행도 수정했다.

## 남은 제품 경계

- 각도=시작 시간인 궤도 배치와 원호형 상세 노트 편집은 아직 설계 단계다. 0.9 UI는 계층형 자유 캔버스다.
- 전체 engine은 prepared PCM playback이다. 연속 realtime graph 변경, plugin crash isolation/PDC, 모든 외부 장치·plugin 호환 검증을 완료하지 않았다.
- MCP의 모든 GUI 편집에 대한 동등한 command coverage는 아직 없다. 현재 구현된 tool/operation만 노출한다. Save는 동기 응답이고 대용량 파일 저장의 별도 job화는 후속 작업이다.
- 외부 LLM은 사용자가 별도로 연결한다. 이번 검증은 local stdio MCP와 실제 native 앱의 연결이며 인터넷 서비스나 hosted agent를 배포하지 않았다.

## 배포

검증한 Release executable로 로컬 `dist/써클러.app` 0.9.0/build10을 구성하고 이전 0.8.0을 archive에 보관했다. `scripts/package-app.py`는 임시 bundle을 서명·검증한 뒤 기존 bundle을 보관하고 교체하므로 실행 중인 executable의 bytes를 직접 덮어쓰지 않는다. bundle 정보·서명·소스 hash와 바이너리 UUID는 `generated/0.9-release-evidence.json`에 기록했다. 서명이 완료된 native 실행과 모든 제품 기능의 완성을 동일하게 취급하지 않는다.
