## 기존 증거와 측정 경계

- [build237 native](0.80-build237-native.md)는 700×900pt·40pt 콘솔·500행에서 100건/약 6.5건/s 입력의 앱 내부 `playback.frameCount` **43.67/42.96 count/s**, 접힌 콘솔 **53.22/53.16 count/s**를 보였다. 두 번째 비율 80.80%는 사전 80% 경계와 가깝다. `qa/measure-canvas-playback.py`와 `CanvasFrameTiming`도 메인 루프/드로우 callback 진단이며 compositor-present FPS가 아니다.
- [build231 writer soak](0.80-build231-movie-audit.md)는 장치 없는 합성 1920×1080·600초 H.264/AAC **18,000/18,000** frame, PTS/PCM/메모리를 통과했다. 실제 AppKit 창·출력 helper·compositor·앱 녹화의 10분 증거로 대체하지 않는다. [build211 실제 앱 38초](0.80-build211-final2-native.md)는 PTS·AAC 분석 도구의 작동 확인 자료다.
- 이용 가능 도구: `/usr/bin/xcrun`, `/usr/bin/swiftc`, `/usr/bin/afconvert`, `/usr/bin/vmmap`, `/usr/bin/sample`, `ps`; `ffprobe`는 현재 PATH에 없음. `qa/inspect-movie-timing.swift`는 전체 픽셀 디코드·PTS·동일 인접 프레임·첫 A/V PTS를, `qa/inspect-movie-audio.py`는 48kHz stereo PCM과 시작/중간/끝 RMS를 낸다. `qa/inspect-movie-soak-counter.swift`는 합성 15-bit 카운터 전용이므로 실제 앱 MP4에는 사용하지 않는다.

## 실행 순서와 판정 — 전부 PENDING

1. **격리/신원.** 다른 native QA 앱의 종료·socket 정리와 원본 해시 확인을 마친 뒤 시작한다. `dist/써클러.app`의 build239·arm64·`codesign --verify --deep --strict`·실행 파일 SHA-256을 기록한다. Git-ignored `qa/generated/r80-build239-performance/`에 **새** QA 앱 사본을 만들고 고유 bundle ID(예: `com.circlr.build239perfqa`)·전용 Application Support/Agent socket을 지정하고 문서 유형을 제거한 후 ad-hoc 재서명한다. 설치 앱/사용자 프로젝트/시스템 기본 오디오 장치·디스플레이 설정은 건드리지 않는다. App 내에서만 작동하는 출력(`BuiltInSpeakerDevice`가 조회·시작되면 우선)을 선택한다. 앱 snapshot의 bundle/build/socket, 기기 기본 UID 전후, 원본/QA 서명·해시를 증거로 남긴다. 기존 QA 앱과 동시 실행하지 않는다.
2. **표시 프레임.** 같은 번들 `f0r h3r`, 같은 카메라·창 700×900pt, 40pt 콘솔, 500행 activity를 사용한다. 출력 `ready/playing` 후 무입력/콘솔 펼침 **60초**, read-only 실패 조회 100건을 **실제 6건/s 이상** 처리하는 콘솔 펼침 **20초**, 콘솔 접힘 **20초**를 각각 Stop→Play의 동일 `접속 · DJ Intro`에서 재현한다. 100건은 각 20초 창의 시작부터 연속 전송하고 실제 입력 구간만 성능 비율에 사용한다. 각 구간의 앱 snapshot·벽시계·처리율·`qa/measure-canvas-playback.py --socket <QA_SOCKET> --seconds <60|20>`을 보관한다. 동시에 Instruments의 앱별 present/frame/hitch 계측을 같은 길이로 녹화한다. 시작 전 `xcrun xctrace list templates`와 `xcrun xctrace list instruments`로 이 호스트가 제공하는 **Core Animation frame presentation/FPS 또는 Animation Hitches** instrument와 export 필드를 확인한다. 예시 명령은 `xcrun xctrace record --template 'Animation Hitches' --attach <QA_PID> --time-limit 20s --output <QA_DIR>/expanded.trace`; `xcrun xctrace export --input <QA_DIR>/expanded.trace --toc`와 해당 table XML을 보존한다. 해당 template에 실제 *앱별 presented frame timestamp/FPS*가 없으면 hitches를 FPS로 환산하지 않고 compositor FPS는 **미검증**으로 둔다. 외부 화면 캡처의 요청률·앱 내부 count·MP4 FPS도 compositor FPS로 부르지 않는다.
3. **표시 성능 사전 기준.** frame presentation 자료가 존재하면 각 구간의 유효 display cadence·P95 간격·100ms 초과 hitch 수를 계산하고 원자료와 계산 스크립트/식을 남긴다. 60Hz 목표 화면에서는 무입력 평균 ≥50fps, 로그 유입 펼침 평균 ≥40fps 및 같은 세션 접힘 대비 ≥80%, P95 present 간격 ≤33.33ms, 100ms 초과 hitch 0을 PASS로 둔다. 실제 디스플레이 refresh가 60Hz가 아니면 목표를 refresh와 앱 애니메이션 정책에 맞춰 **측정 전에** 기록·조정한다. 요청률 <6/s, 출력 `ready/playing` 실패, 창 가림, 다른 섹션/카메라, Instruments의 전체 시스템 집계뿐인 결과는 비교 무효/OPEN이다. 경계 ±5% 이내 결과는 동일 조건 1회 재현하고 둘 다 보고한다.
4. **실제 앱 MP4 10분.** QA 폴더에 최소 4GiB 여유를 확인하고 동일 QA 앱에서 16:9 창을 가능한 범위에서 1600×900pt로 설정해 Retina 2× 캔버스의 최종 **1920×1080** 출력을 노린다. 창/화면이 허용하지 않으면 최대 실제 해상도를 기록하고 1080p 항목을 OPEN으로 둔다. `f0r h3r` 곡 루프·감상 모드/팔로우로 Save panel에서 QA 폴더의 새로운 이름에 ⇧⌘R 시작, output `ready/playing`을 확인하고 **600초** 후 ⇧⌘R 종료한다. 앱 `movie.submitted/encoded/skipped/dropped/pending`, playback seconds, section/loop iteration, 출력 상태를 시작·매 30초·종료에 snapshot으로 저장한다. PID별 `ps -o rss= -p <QA_PID>`와 해당 출력 helper PID의 RSS를 같은 간격에 기록한다. 60초 warm-up 이후 각 PID RSS 증가 ≤512MiB, 종료 시 pending 0, 파일 publish 후 `.circlr-movie-*` stage 0을 임시 누수/정리 기준으로 삼는다. crash·앱 응답 정지·출력 timeout·실제 녹화 내부 dropped/skipped >0은 FAIL로 남긴다.
5. **독립 파일 판독.** 파일 SHA-256과 `afinfo`/codec 정보를 보존한다. `xcrun swiftc -parse-as-library qa/inspect-movie-timing.swift -o <QA_DIR>/inspect-movie-timing` → `<QA_DIR>/inspect-movie-timing <QA_DIR>/actual.mp4 > <QA_DIR>/timing.json`; `python3 qa/inspect-movie-audio.py <QA_DIR>/actual.mp4 > <QA_DIR>/audio.json`. MP4의 H.264/AAC, 실제 1920×1080(가능했을 때), 약 600초(수동 정지 오차 ±3초), 영상 평균 ≥29fps, P95 PTS 간격 ≤50ms, 최대 간격 ≤66.67ms, 중복/역행 PTS 0, **해독 픽셀 기준** 인접 동일 프레임 0, 첫 A/V PTS 차 ≤25ms, AAC 48kHz stereo·시작/중간/끝 1초 RMS >0, decoded PCM/영상 길이 차 ≤100ms를 PASS 기준으로 삼는다. 앱 encoded와 독립 decoded 차가 1을 넘으면 원인 확인 전 FAIL; 1 차이도 종료 경계로 따로 기록한다. 시작/중간/끝 PNG의 실제 궤도·섹션 변화와 독립 플레이어 시청을 남긴다. 첫 PTS·PCM RMS는 중간/끝의 **지각적** A/V 동기를 증명하지 않으므로 청감·시청 확인 없이는 그 항목 PENDING이다.
6. **정리/판정.** QA 앱만 Stop→⌘Q(미저장 변경은 QA 사본만 버림), PID/helper/socket 0을 확인한다. 시스템 기본 입출력 UID, 원본 실행 파일/번들 서명·hash 불변을 기록한다. trace/XML, 30초 상태·RSS CSV, 독립 JSON/MP4/SHA256SUMS, 시작/중간/끝 화면, 실패 시각을 Git-ignored `<QA_DIR>`에 보관하고 실행 보고서에서 **compositor·앱 MP4·물리 청취** 판정을 각각 분리한다. 임의 사용자 조작/TCC가 필요하면 그 항목만 BLOCKED로 표시하고 장치 독립 부분은 계속한다.

`xctrace` template/권한/내보내기 필드와 실제 1080p 창 가능 여부는 아직 조회·실행하지 않았다. 위 기준은 이번 최종 앱 QA의 **사전 판정선**이며 통과 결과가 아니다.
