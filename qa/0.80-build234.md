## 자동 검증

- **MIDI:** 반복 종료 뒤 메인 루프 호출과 늦은 Note On/Off를 합성 timestamp로 재현했다. 수정 전 신규 회귀의 7개 assertion이 실패했고, 수정 뒤 마지막 반복 경계에서 노트와 take가 종료됐다. 저장된 노트·반복 수·Undo와 preview release를 검사했다. 다른 녹음·영상 시작 경로가 활성 capture를 우회하지 못하도록 모델 명령과 저장 패널 복귀 시점에도 상호 배제한다. 신규 `CaptureMutualExclusionTests` 6/6, 관련 `MIDIRecordingFidelityTests` 5/5 및 `RecordingDocumentBoundaryTests` 5/5가 통과했다. 물리 MIDI 장치나 실제 소리 검사는 아니다.
- **상단 UI:** MIDI/오디오 take 메뉴와 MP4 `영상 녹화`를 구분하고, 선택 대상 없음·장치 준비·활성 상태를 표시한다. 녹음 중 selection이 바뀌어도 활성 take 대상이 새 selection인 것처럼 표시하지 않는다. 신규 `TakeRecordingEntryTests` 2/2와 앱 빌드가 통과했다. 화면 픽셀과 접근성은 별도 native QA로 판정한다.
- **내부 MCP:** 앱 소유 `Process`의 stdin/stdout만 사용해 별도 helper를 시작한다. private socket과 capability는 한정된 초기 stdin frame으로만 전송하고, 자식은 같은 UID와 실제 부모 PID를 확인한다. 실제 자식 프로세스의 선택 MIDI 편집→Undo→재적용→nonzero WAV, STOP/완료·만료·문서 교체·child 비정상 종료, 응답 대기와 stdin 정지 경계를 신규 `TrustedMCPHelperProcessTests` **8/8**로 검증했다. 기존 완료 turn의 수락된 bounce가 STOP과 달리 유지되는 회귀도 통과했다. 이는 오프라인 앱 내부 권한 경계이며 사용자 Codex 계정 대화나 모델 turn 검증이 아니다.

최종 소스의 `./scripts/swift-local.sh test --scratch-path .build/build234-integration-final` 전체 실행은 **1,253개·15 skip·실패 0**이었다(`/tmp/circlr-build234-swift-final.log`, SHA-256 `7e857abe35ee360072e1bbdf407d250392032e2eb211001e77b1cf4998049923`, 251.3초). `python3 -m unittest discover -s mcp -p 'test_*.py' -q` **47개**, `python3 -m unittest discover -s Tests -p 'test_mcp_*.py' -q` **39개**도 실패 0이다. helper 관련 테스트는 실제 실행 파일 경로를 환경 변수로 지정했고 전체 로그에서 8개가 skip 없이 실행된 것을 확인했다.

독립 DAW/UI 리뷰가 대체 녹음 명령 경로의 동시 시작 및 녹음 중 selection 전환 시 잘못된 대상 문구를 찾았다. 두 문제를 수정·회귀 추가했다. 독립 보안 리뷰에서 P0/P1은 보고되지 않았으나, 동일 UID의 느린 비인증 연결이 직렬 socket queue에서 최대 3초를 차지할 수 있는 **P2 가용성 문제**가 남았다. 사용자용 AI 연결의 G0 전 해결 대상이며 이번 내부 helper의 보안 완료로 표현하지 않는다.

## 패키지·실제 앱

`./scripts/build-app.sh`는 **0.80.0/build234** arm64 앱과 다섯 오디오 helper, 새 내부 `circlr-trusted-mcp-helper`를 패키징했다. `/tmp/circlr-build234-package.log` SHA-256은 `4f78daaf1a71ae94ab568df9911ec6f8394f06cc99ef2050a2b8c80cc704827e`다. 주 실행 파일 SHA-256은 `48e13ad54aedb965f64470ed313340a320c8f7cd84f172ef65b994505ca8dafb`이다. `codesign --verify --deep --strict --verbose=2`는 앱과 **6개 자식 실행 파일**에서 통과했고, 전부 arm64 Mach-O다. `CFBundleShortVersionString=0.80.0`, `CFBundleVersion=234`를 패키지에서 직접 읽었다.

동봉 `Resources/Codex`의 manifest **25/25** hash, 데모 manifest **26/26** hash와 source/package byte 비교(Codex 26파일·Demos 27파일)가 일치했다. 검증 과정에서 소스 `Codex` 폴더의 Python `__pycache__` 두 파일은 빌드 산출물이라 source/package 비교에서 제외했고, 실제 동봉 manifest 파일은 모두 검증했다. `build-icon.py`가 다시 만든 tracked `Resources/Assets.car`는 패키징 뒤 HEAD의 원본으로 복구했다. 패키지 무결성은 GUI 동작·청취의 증거가 아니다.

[격리 실제 앱 QA](0.80-build234-native.md)는 별도 bundle ID와 Application Support를 쓴 서명된 QA 사본에서 700/720/900/1440pt 상단 녹음·영상·감상·서클 추가의 픽셀/AX 비겹침, 대상 미선택의 disabled 메뉴와 선택 대상의 MIDI/오디오 메뉴를 확인했다. MIDI take를 실제로 시작·정지했고, 입력을 연주하지 않아 **0개 note**를 기록했다. 영상 버튼은 활성 take 중 disabled였다. 앱 전용 `BuiltInSpeakerDevice`의 번들 데모 재생 시계가 00:00.3→00:12.3 진행하고 정지했다. 실제 귀로 들었거나 입력 PCM을 얻었다는 뜻은 아니다. 오디오 take는 기본 입력 Scarlett을 보존하기 위해 실행하지 않았다.

동봉 데모를 다시 연 정지 00:00.0의 1440×900pt/720×900pt 전체 창 PNG를 [한영 README](../README.md)에 사용하고 [화면 출처·SHA](../docs/images/README.md)에 기록했다. QA 앱/child PID와 전용 socket은 종료 후 모두 **0**이었으며, 읽기 전용 장치 조회의 시스템 기본 Scarlett UID hash는 이전과 동일했다. 이 native 결과는 물리 장치 호환성이나 0.80 출고 판정으로 확장하지 않는다.

## 열린 gate

이 Mac에서 `Scarlett 6i6 USB`가 기본 입출력으로 인식되는 사실은 호환성이나 청취의 증거가 아니다. Focusrite의 macOS 26 세대별 표와 현재 기기의 세대 식별 차이를 [출력 조사](0.80-output-investigation.md)에 분리했다. native QA는 시스템 기본값을 건드리지 않고 앱 전용 Mac 내장 출력을 사용한다. 실제 물리 입력 take·스피커 청취가 없으면 OPEN으로 남긴다. 긴 MP4, 0.80 전체 제작·저장·복구·반복/고밀도 매트릭스, 사용자 계정의 앱 내 AI turn 역시 OPEN이다.
