## 자동 검증

합성 status 이벤트를 `AppStore.midi`에 전달해 **동일 pitch·다른 채널**, 동일 채널 재어택, velocity=0 Note On의 Off 해석, 반복 경계 분할과 녹음 종료 flush를 검사했다. 생성된 take의 note 수·원래 velocity·beat·length·활성 lane·Undo를 비교했다. 녹음 중 preview 명령은 매 Note On을 재어택하고 마지막 활성 채널의 Off에서만 release하는지 관찰했다. 신규 `MIDIRecordingFidelityTests` 4개, 기존 `RecordingDocumentBoundaryTests` 5개와 `AuditionTransportTests.testWarmRetriggerSendsOffBeforeNewOnAndReusesBackend` 1개가 전용 scratch에서 통과했다. `AuditionTransport`는 비동기 desired-state 방식이므로 helper 시작 전에 몰린 매우 빠른 입력의 실제 발음 개수는 이 테스트가 보증하지 않는다.

MCP `circlr_context`는 **기존 native `snapshot`을 한 번** 조회하고 project ID·music/layout revision, 활성 편곡안과 bounded use, 선택 주소/use, 곡·편곡안·트랙 ID/이름, 활성 capability와 짧은 job·재생·녹음·출력 상태만 돌려준다. 목록은 total/returned/truncated를 제공하며 전체 프로젝트 경로·asset·pattern·note·job message/path는 기본 응답에 넣지 않는다. Swift `CircleAddress`의 앨범/사운드 object 형식과 group parent, 비정상 숫자, `--read-only`, `--request` 경계를 테스트했다. 최종 `python3 -m unittest discover -s mcp -p 'test_*.py' -q`: **47개 통과**(`mcp.test_server`는 34개). `python3 -m unittest discover -s Tests -p 'test_mcp_*.py' -q`: **39개 통과**. 독립 MCP 보안·정확성 리뷰에서 처음 발견된 앨범 주소와 큰 숫자 오류는 수정 후 실제 QA snapshot projection으로 재검사했다.

저장된 [QA232 native snapshot](generated/r80-qa232-model-native/preflight-snapshot.json) SHA-256 `ad9273e07f520af0d4c92d4523170a942ef4bb267bdd69cec746f943cc6259a1`의 compact native wire는 **13,051B**, 같은 request ID로 만든 compact context wire는 **2,355B**였다(**82.0% 감소**). pretty source 파일은 23,454B다. 이는 한 번의 응답 크기이며 모델 token 청구량이나 전체 turn 절감량의 측정치가 아니다. 실제 편집에는 원본 `snapshot`/대상 `inspect`와 최신 revision이 계속 필요하다.

독립 Swift/UI 리뷰는 MIDI의 두 번째 채널 Note On 미리 듣기 누락과 VoiceOver 팔로우 대상 누락을 발견했다. 둘 다 수정하고 해당 회귀를 더했다. 재생 중 실제 청취·물리 take·화면의 모든 폭을 이 자동 검증으로 확장해 판정하지 않는다.

최종 변경을 포함한 `./scripts/swift-local.sh test --scratch-path .build/build233-integration-tests` 전체 실행은 **1,236개·15 skip·실패 0**이었다(`/tmp/circlr-build233-swift-final.log`, SHA-256 `72a2376dfac4dab21ec29266958c15d65bd64888d545baac794d93af71c03641`, 242.924초). 앞서 리뷰 수정 전 전체 실행도 1,235개·15 skip·실패 0이었으나 최종 판정은 수정 뒤 실행을 기준으로 한다. 최종 독립 코드 재검토에서 추가 차단 결함은 보고되지 않았다.

## 빌드·native QA

`./scripts/build-app.sh`는 **0.80.0/build233** arm64 앱과 다섯 audio helper를 패키징했다. 빌드 로그 `/tmp/circlr-build233-package.log`의 SHA-256은 `8a3d1b35de45521930771a020c96c8557d2d4ec7175c52452467669546f84c0e`다. `codesign --verify --deep --strict`가 통과했고, 주 실행 파일 SHA-256은 `880e6bcffc23ec8454e0c7df00ab574577caf912dd8567042eb1c6c4c51051b2`다. Codex kit manifest의 **25/25개 hash**가 동봉 파일과 맞았고, 7파일 `f0r-h3r.circlr`는 source/package byte hash가 일치했다. 데모 manifest SHA-256은 `a75ea9f2f3917f82184ba94c31e071905c0c6a1bfa2e90259ad554eaa5c794d7`다. `build-icon.py`가 다시 만든 tracked `Resources/Assets.car`는 패키징 후 HEAD의 원본으로 복구했다. 이 package 검사는 앱 화면 동작의 증거가 아니다.

별도 [build233 native QA](0.80-build233-native.md)는 격리 서명 앱의 **700/720/900/1440pt** 전체 창에서 지정한 팔로우 대상·상태, 주요 상단 버튼과 7섹션의 픽셀·AX 가시성을 확인했다. 700pt는 곡/섹션/고정 각각 following/off, 720pt 재생은 셋의 suspended/resumed, 900/1440pt는 SONG following을 실행했다. 실제 재생 시계가 00:02.6→01:06.6 진행했고 앱에서만 Mac Studio 내장 출력을 지정했다. 시스템 기본 Scarlett UID는 종료 후에도 불변이었다. 이는 **소리가 실제로 들렸다는 청취 판정이 아니다**. 4개 폭×3대상×3상태의 완전한 행렬도 아니며 다른 곡·고밀도·모든 줌은 미검증이다.

같은 격리 앱의 패키지 내 MCP `circlr_context`를 `--read-only` 세션에서 실제 호출했다. project revision **1**, layoutRevision **0**, runtime build **233**을 포함한 요약이 왔고 경로·asset·pattern·note·job 경로가 없었다. QA 앱·helper PID **0**, 전용 socket **없음**, 원본/QA deep strict 서명이 종료 뒤에도 유효했다. README의 가로·세로 새 PNG는 QA 앱을 재시작해 번들 데모를 다시 연 **정지 00:00.0** 전체 창에서 변환했으며 [이미지 출처](../docs/images/README.md)에 원본·복사본 SHA-256을 남겼다.

## 열린 gate

Mac Studio의 시스템 기본 출력은 Scarlett 6i6 USB일 수 있지만 그 장치의 최신 macOS 적합성은 확인되지 않았다. 실제 앱 QA가 필요하면 **앱 전용 출력만** Mac 내장 장치로 선택하고 시스템 기본값은 유지한다. 물리 청취 및 입력 take는 직접 확인하지 못하면 미검증으로 남긴다. 0.80의 장시간 실제 창 MP4, 전체 제작·반복·플러그인·고밀도 화면, 제품 내부 사용자 Codex 계정 turn도 닫히지 않았다. 외부 MCP 도구 추가를 계정 대화 기능 출고로 표현하지 않는다.
