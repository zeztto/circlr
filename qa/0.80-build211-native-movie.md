## 35~40초 녹화와 독립 검사

앱의 Save 패널을 통해 `qa/generated/r80-build211-native-movie/build211-native-38s.mp4`를 지정하고 38초 뒤 ⇧⌘R로 녹화를 마쳤다. UI는 **`영상 저장 완료 · 1138프레임 · build211-native-38s.mp4`**를 표시했다. 이 상태의 원본 window PNG `build211-save-notice-window.png` SHA-256은 `0bb32d5264cc9b5193f269b28f3769548d027183f0e986f3eb36edc861acb249`다. MP4는 **6,133,534 bytes**, SHA-256 **`bcf9e2226afed52d2b08ee259433450dd8952bb65a426f40356e32962ee384fb`**다.

`swiftc -parse-as-library qa/inspect-movie-timing.swift`로 만든 별도 AVFoundation decoder가 H.264 영상을 **1138프레임 모두 실제 픽셀로 해독**했다. 따라서 **이번 38.006667초 파일은 UI 1138 = decoded 1138**로 일치한다. build210의 유사한 37.29875초 파일에서 관측된 UI 1118 / decoded 1117 차이는 이번 동일 데모·유사 길이·수동 종료 조건에서 재현되지 않았다.

별도 프레임 추출기의 시작 **0.096667초**, 중간 **18.498333초**, 끝쪽 **36.790초** PNG에서 곡 궤도·서클 진행·섹션 전환을 확인했다. 인접 영상 전체의 픽셀 해시는 모두 달랐다. 68.33ms 단일 간격은 MP4의 측정값이며 눈으로 본 끊김이나 청감 동기 실패로 확정하지 않는다. 기존 0.70의 2프레임 초과 gap 0 목표와 비교하면 추가 확인이 필요한 잔여 위험이다.

`afinfo`는 stereo 48kHz AAC, 유효 audio **1,824,320 PCM frames**를 보고했다. `qa/inspect-movie-audio.py`가 `afconvert`로 별도 해독한 PCM 길이는 **38.006667초**, peak **0.73218**, RMS **0.09851**이었다. 1초 창의 시작 0초·중간 19.003초·끝쪽 34.206초 RMS는 각각 **0.07368 / 0.10849 / 0.11229**로 모두 nonzero다. 이 수치는 실제 스피커 소리의 물리 청취, 별도 플레이어 완주, 중간·끝의 지각적 AV 동기 판정이 아니다.

## 실제 build211 화면과 정리

재생 Stop 뒤 앱 종료 대화상자에서 격리 데모 세션의 저장하지 않은 변경을 버렸다. 최종 `ps`에서는 build211 QA 앱/helper와 이전 build210 QA 앱 프로세스가 모두 0개다. QA 앱 strict deep 서명은 실행 후에도 통과하고 원본 앱 tree·실행 파일 SHA는 복사 전과 같다. 격리 저장소에는 `Agent/selected.json`과 `recovery-v2.lock`만 남았다. 검증 중 CUA가 이전 build210 QA 앱의 시작 화면을 다시 연 일이 있어 앱 식별자와 `ps`로 확인하고 해당 앱을 곧바로 종료했다. 이후 build211 bundle ID로 다시 연결해 211 버전·출력 선택을 확인한 뒤 녹화했다. 사용자 앱 및 프로젝트는 열거나 교체하지 않았다.
