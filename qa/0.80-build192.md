# 0.80 build192 · 포트 편집 복구와 내장 출력 검증

상태: **부분 PASS / 0.80 출고 승인 아님** · 2026-09-23. `release/0.80.0`의 0.80.0/build192 앱을 검사했다. 원본 데모·사용자 설치 앱·시스템 기본 출력 설정은 바꾸지 않았다.

## 빌드와 자동 검증

- 전체 Swift 테스트 **1084개 실행·11개 skip·실패0**. `qa/generated/r80-build192-final-suite.log` SHA-256 `25f3183d1b6703d57be0f81457496d29a2415c0b32872ec48e42767ac71225c7`. MCP Python **39/39**, agent kit **9/9**도 통과했다.
- 앱과 다섯 helper의 production 빌드, arm64 실행 파일, `CFBundleVersion=192`, 앱의 `codesign --verify --deep --strict`를 확인했다. 빌드 로그 `qa/generated/r80-build192-build.log` SHA-256 `9a1b69e4c39561125dcca21068804996a972b6df4011f6fd292805bba896f900`.
- 최종 앱의 `circlr-output-worker`로 **명시적 Mac 내장 스피커** AudioQueue native 테스트 **5/5**를 실행했다. 정지·3초 스트리밍·유한 재생 종료·루프 교체·루프 해제의 worker/host 상태와 샘플 경계를 검사했다. 테스트 뒤 QA 앱과 output worker의 잔류 프로세스는 없었다. 로그 `qa/generated/r80-build192-audio-audit.log` SHA-256 `234ce14fccacab18baa6a82dbef1c343a897d1c70982f42b5309404ea1112ffd`. 테스트 신호는 무음이므로 **실제 청취 증거가 아니다**.

## 실제 앱·격리 곡 검증

- [QA 준비 도구](prepare-port-focus-qa.py)로 앱/곡을 분리했다. 첫 섹션의 FX 위성 하나를 x=12000으로 옮기고 프로젝트 ID만 바꿨다. 음악 데이터는 동일하다. `qa/generated/port-focus/build192/package.json`에 앱/곡 tree hash, 원본/사본 manifest SHA, 서명과 변경 좌표를 기록했다. 원본 manifest SHA-256 `a75ea9f2f3917f82184ba94c31e071905c0c6a1bfa2e90259ad554eaa5c794d7`; 검증 뒤 원본 앱·데모와 실행용 QA 곡의 hash가 준비 시점과 일치했다.
- 문서 폴더 권한 요청을 피하려고 별도 `~/Library/Application Support/circlr-portfocus-qa/build192/`에 같은 서명 앱/곡을 복사하고 해시 일치를 확인했다. 실제 앱에서 `버전 0.80.0 · 빌드 192`, `f0r h3r 열기 완료`를 확인했다.
- 약 **700×900** 창에서 곡→`접속 · DJ Intro` 궤도로 이동했다. 먼 FX 위성이 중심 섹션을 점으로 줄이지 않았고, 가까운 위성·섹션 IN/OUT과 두 줄 상단 조작을 볼 수 있었다. 캔버스 접근성 트리에서 `P`는 섹션 IN을, `Tab`은 OUT을 선택했다.
- build191 실패 경로를 다시 실행했다. IN 선택 후 **`Return`**을 누르자 섹션 내부 연결 편집기가 열리고 IN 포트, 대상 검색 6개, 기존 연결 1개가 나타났다. 다시 섹션으로 돌아와 OUT 선택 후 도구의 **`연결 편집`** 버튼을 눌러 OUT 포트의 같은 편집기를 확인했다. 이때 검색 필드에 키보드 포커스가 놓였다. 두 경우 모두 실제 화면과 접근성 트리에서 확인했다.
- QA 앱 종료 뒤 해당 프로세스와 output worker의 잔류는 없었다. 기존 실행 중인 다른 QA 앱은 건드리지 않았다.

## 앱 전용 내장 출력의 실제 재생·정지

- 같은 서명 QA 앱을 다시 열고 **동봉된 최신 `f0r h3r` 데모**를 불러왔다. 출력 설정에서 `Mac Studio 스피커`를 앱 전용으로 선택했다. 설정 화면은 선택 전후 `현재 시스템 기본값: Scarlett 6i6 USB`를 표시해 시스템 기본 장치를 바꾸지 않았음을 확인했다.
- 첫 Play에서 일곱 섹션의 사운드 준비 뒤 `출력 큐 준비 중 → 출력 장치 시작 중 → 마지막 재생 확인 장치: Mac Studio 스피커 → 재생 중`으로 전환했다. 재생 시계가 `00:01.6`에서 `00:05.6`으로 진행했다. Stop 뒤 `이전 출력 정리가 끝났습니다`와 `00:00.0`을 확인했다.
- 바로 다시 Play하자 같은 Mac Studio 스피커로 재연결해 재생 시계가 `00:00.4`에서 `00:03.3`까지 진행했다. 두 번째 Stop도 출력 정리 완료 상태로 돌아왔다. 출력 설정을 다시 열어 시스템 기본 Scarlett/앱 전용 Mac Studio 선택과 마지막 확인 장치를 재확인했다.
- QA 앱 종료 시 뜬 미저장 변경 안내는 **`변경 버리기`**로 마쳤다. 앱/worker 프로세스 잔류가 없고 원본 앱·동봉 데모·실행용 QA 사본의 해시가 준비 시점과 일치했다. 실제 스피커의 소리는 이 원격 UI 관찰에서 판정할 수 없으며 오디오 내용·dropout·지연 측정도 하지 않았다.

## 짧은 영상 저장과 독립 파일 검사

- 별도 새 QA 세션에서 동봉 데모와 앱 전용 `Mac Studio 스피커` 선택을 다시 확인한 뒤, 실행용 QA 폴더에 `r80-build192-short.mp4`를 저장했다. 실제 앱은 `영상 녹화 중 · 캔버스 + 음악`에서 `영상 저장 완료 · 373프레임`으로 바뀌고 `702×750 · H.264/AAC · 누락 0프레임`을 표시했다. 파일 SHA-256은 `bd15a06f269b4f9a96fd28800417c4711565a52cb415ac73b557b5472c8e06d1`; 동일 해시의 검토 사본은 Git 제외 `qa/generated/r80-build192-short.mp4`다.
- [독립 영상 판독](inspect-movie-timing.swift)에서 **12.4993초·702×750·373개 디코드 프레임·평균 29.856fps**, 중복 PTS 0, 인접 동일 픽셀 프레임 0, 66.7ms 초과 간격 0, 최대 간격 **61.67ms**, 간격 P95 **53.33ms**였다. 첫 video/audio PTS는 모두 0이다. `qa/generated/r80-build192-movie-timing.json` SHA-256 `fe44496ffc7b6c9bcd8e8620b7fc5c059cf59945551d3b0b700320331027beb7`.
- [독립 오디오 디코드](inspect-movie-audio.py)는 stereo 48kHz, 599,965 PCM 프레임, RMS **0.0740**, peak **0.6077**을 확인했고 시작·중간·끝 구간 모두 nonzero다. `qa/generated/r80-build192-movie-audio.json` SHA-256 `14a810d8feaca99fe9ee37eac3d54c71891d48132433009e0f66d931b4165192`.
- 6초와 12초 프레임을 따로 열어 궤도·노드·재생 표시가 영상에 들어갔음을 관찰했다. 702pt 너비의 15트랙 섹션 그래프는 여전히 조밀하다. 평균 FPS가 약 30이어도 P95 53ms의 불규칙한 간격이 남으므로 **부드러운 움직임의 PASS 근거가 아니다**. 실제 시청·청취와 중간/끝 AV 동기, 1080p·10분·고밀도 장시간 성능은 별도로 검사해야 한다.

이 검증은 포트 편집, 내장 출력 worker, 실제 앱의 **두 차례 재생·정지 상태 전이**, 짧은 MP4 파일 판독 범위다. 실제 곡의 **내장 스피커 물리 청취**, 출력 timeout 뒤 GUI 복구, Scarlett의 세대·장치 호환성, 영상의 실제 시청·청취와 장시간 FPS, 전체 제작, 900/1280pt 및 실제 세로 디스플레이는 완료하지 않았다. 구형 Scarlett의 정상 출력은 0.80 필수 성공 조건이 아니지만 안전한 실패·복구는 남아 있다. `v0.80.0` 태그·GitHub Release는 아직 만들지 않는다.
