## 확인한 경계

`MovieRecording.swift`는 실제 창의 `captureMovieFrame`을 받아 `CanvasMovieWriter`에 넘기며, 30 Hz 캡처는 출력 helper의 새 하드웨어 시각을 요구한다. `CanvasMovieCapture.swift`는 AppKit 캔버스를 최대 1920×1080 raster로 그린다. Writer는 한 장만 대기시키는 serial encoder queue, H.264/AAC `AVAssetWriter`, 숨긴 임시 MP4에서 최종 파일로의 publish를 사용한다. 현재 `CanvasMovieWriterTests`는 대략 0.5–1.4초의 저해상도 합성 프레임과 종료·루프 경계를 검사한다. 최종 build211 실제 앱 MP4는 1440×800·37.980초·UI/독립 디코드 1138/1138·nonzero AAC·최대 gap 60ms였다. 이들은 장시간 1080p의 큐 압력·메모리 증가·AAC 끝부분을 검증하지 않는다. [최종 실제 앱 기록](0.80-build211-final2-native.md), [0.80 게이트](../docs/releases/0.80.0.md).

## 다음 한 단계: 출력 장치 없는 1920×1080·10분 writer soak

`Tests/CirclrAudioTests/CanvasMovieWriterTests.swift`에 opt-in `testTenMinuteFullHDLoopSoak`을 구현했다. 1초 길이의 nonzero stereo PCM을 `PlaybackLoopPCM`으로 반복하고, 각 frame에서 15-bit 시각 카운터가 달라지는 합성 `CGImage`를 **30 Hz 목표 시각에 600초** 제출한다. AppKit 창, `Playback`, CoreAudio output/input, Scarlett, 시스템 기본 오디오 설정은 사용하지 않는다. 30초마다 writer 제출·인코딩·누락·큐·최대 인코딩 시간·RSS와 합성 프레임 생성/스케줄 지연을 JSONL로 남긴다. 마지막에 `finish(seconds:600)` 후 임시 stage를 확인하고 별도 `AVAssetReader`로 전체 영상의 **보이는 픽셀을 해독·해시**하며 오디오를 구간별 PCM으로 해독한다. `CIRCLR_MOVIE_SOAK=1`일 때만 실행해 일반 전체 suite를 10분 늘리지 않는다.

첫 10분 실행에서 호스트 wake-up이 늦었을 때 원래 구현은 `canAcceptFrame`이 false인 frame을 버렸다. 수정된 테스트는 **원래 frame PTS를 유지**하면서 순서대로 catch-up 제출하고, encoder queue가 차 있으면 `waitUntilIdle` 뒤 제출한다. 따라서 writer의 18,000-frame 지속성은 호스트 스케줄러의 일시 지연과 분리해 검사한다. catch-up은 실제 앱이 놓친 시각을 소급 촬영했다는 뜻이 아니다. `inspection.json`의 `writerIntegrityStatus`와 `realtimeSchedulerStatus`를 별개로 남기며, scheduler FAIL은 XCTest writer 성공 여부와 관계없이 **실제 앱 영상 출고 게이트 OPEN**으로 취급한다. 이 QA 작업의 제품 바이너리는 여전히 build230이며 build231 앱을 만들지 않았다.

수정된 writer 10분 검증 명령(실행 완료):

```sh
CIRCLR_MOVIE_SOAK=1 ./scripts/swift-local.sh test --scratch-path .build/r80-movie-soak --filter 'CirclrAudioTests.CanvasMovieWriterTests/testTenMinuteFullHDLoopSoak'
```

예상 소요는 실시간 제출 **10분**과 H.264 최종화·전체 픽셀 decode **약 5–20분**이며, 로컬 인코더 성능에 따라 더 걸릴 수 있다. 1920×1080 현재 설정의 목표 비트레이트는 약 14.5 Mb/s이지만 이 합성 카운터는 매우 잘 압축되므로 실제 파일 크기는 훨씬 작을 수 있다. 시작 전 QA 전용 저장소에 최소 4 GiB 여유를 확인하고, 원본 곡이나 사용자 영상 경로를 쓰지 않는다. 출력은 `qa/generated/r80-build231-movie-soak/run-<UUID>/`의 `soak.mp4`, 30초 진단 `diagnostics.jsonl`, writer 수치·독립 전체 프레임 해독·오디오 window·영상 SHA-256을 담은 `inspection.json`이다. 영상 SHA는 1 MiB 단위로 스트리밍 계산해 10분 파일 전체를 메모리에 올리지 않는다. 생성물은 Git 제외, 결과 요약만 QA 문서에 기록한다.

**Writer integrity PASS 기준**: 정확히 1920×1080·600초 근처(±30ms) H.264/AAC가 게시되고, 18,000개 목표 video frame의 writer 제출·인코딩 수와 독립 픽셀 디코드 수가 일치한다. PTS 역행/중복과 2 frame(66.67ms) 초과 gap이 0이고, 인접 presentation frame의 pixel hash가 모두 다르며, 시작·5분·끝 부근 stereo 48 kHz AAC의 RMS가 0보다 크다. 첫 A/V PTS 차는 25ms 이내, 마지막 AAC packet PTS는 목표 끝의 100ms 이내여야 한다. `maximumPendingFrames ≤ 1`, 누락·writer 오류·임시 stage 잔류 0, 60초 warm-up 이후 resident memory 증가가 **512 MiB 이내**, 끝에서 pending 0이어야 한다. 하나라도 실패하거나 `AVAssetWriter`가 완료하지 못하면 writer **FAIL**로 원인/시각/잔류 파일을 기록한다. 메모리 한도는 제품 정책이 아니라 이 단일 QA에서 장시간 누수를 검출할 임시 기준이다.

**Real-time scheduler 별도 판정**: 30 Hz deadline보다 한 frame(33.33ms) 이상 늦은 wake-up이 0이어야 `realtimeSchedulerStatus=pass`다. 이 값은 host/XCTest 타이머의 관찰로 실제 AppKit compositor FPS를 대신하지 않는다. 느린 wake-up이 있어도 수정된 writer 시험은 PTS를 순서대로 채워 인코더 경로를 별도로 검증한다. 실시간 지연이 있으면 `realtimeSchedulerStatus=fail`로 남기고 실제 앱 10분 QA를 계속 연다.

합성 frame의 `generatorP95Milliseconds`·최대값, 30 Hz deadline 지연 횟수, writer의 `maximumEncodeSeconds`, 전체 픽셀 디코더 소요 시간을 분리한다. 누락이 있더라도 generator가 33.33ms를 넘었거나 호스트 스케줄이 늦었다면 **writer 병목으로 단정하지 않는다**. 반대로 generator·스케줄이 여유로운데 writer queue가 차거나 encoder 시간이 늘었다면 writer를 우선 조사한다. 전체 픽셀 해독·해시는 녹화 **후** 수행하므로 그 비용은 10분 실시간 인코딩의 FPS 측정에 섞이지 않는다.

## 첫 10분 실행의 실패 증거 — 유지

수정 전 동일 opt-in 테스트의 `run-81A6217C-4B65-4C45-8527-B7B2507A1E15/inspection.json` 및 `soak.mp4`는 **FAIL**이다. MP4 SHA-256은 **`aa8804f92d73a5be6428d22135001ea06ff81374871dc60035324edd243bc0f1`**이며, 1920×1080·600초 H.264/AAC·18,755,188 bytes였다. 목표 18,000개 중 writer 제출/인코딩·독립 픽셀 decode가 모두 **17,997개**, skipped/dropped **3개**, 2-frame 초과 PTS gap **1개**(최대 **133.33ms**)였다. 최대 schedule lateness **119.63ms**와 한 frame 초과 wake-up **3회**인 반면 generator 최대 **6.97ms**, writer 최대 encode **14.94ms**였다. 첫 30초 진단 snapshot에 이미 dropped 3개가 있어, 해당 누락을 90초 전후로 특정할 수 없다. 이 수치는 스케줄 지연과 누락의 동시 관측이며 한 실행만으로 운영체제 wake-up 지연의 근본 원인이나 실제 앱 compositor 문제를 단정하지 않는다.

## 수정본 10분 장치 독립 writer 결과

수정된 테스트를 위 명령으로 다시 실행해 **1건 통과·실패 0, 총 649.300초**였다. `run-149CEAEC-B9B9-4365-8269-48B1CA1D1D2D/soak.mp4`는 **1920×1080, 600.000초, 18,755,494 bytes**, SHA-256 **`edee62c4648ad049b58d764258093120b8bd7dfddf0c4a1c52855013f6d2d0f1`**이다. 내부 `inspection.json`의 writer 제출·인코딩·전체 픽셀 디코드가 **18,000/18,000/18,000**, 누락·중복 PTS·인접 동일 픽셀·2-frame 초과 gap 모두 **0**, 최대 PTS 간격 **33.333ms**, 최대 대기 프레임 **1**이다. 영상 끝 PTS **599.9667초**, 첫 A/V PTS 차 **0ms**, AAC 첫/마지막 PTS **0/600초**이며 시작·300초·599초 RMS는 각각 **0.056575/0.056568/0.056568**이다. 60초 이후 RSS **334,643,200→335,478,784 bytes**로 약 0.84MB 증가했고, 최대 encode **16.22ms**, generator P95 **2.73ms**, 최대 schedule lateness **13.96ms**, 한 frame 초과 wake-up **0**이었다. `writerIntegrityStatus=pass`, `realtimeSchedulerStatus=pass`다.

별도 프로세스의 `qa/inspect-movie-timing.swift` 전체 픽셀 디코더도 **18,000프레임·30fps**, PTS 중복·동일 인접 픽셀·2-frame 초과 gap **0**, 첫/마지막 video PTS **0/599.9667초**, 첫 A/V offset **0ms**를 기록했다. `qa/inspect-movie-audio.py`는 macOS `afconvert`로 **48kHz stereo, 28,800,000 PCM frames, 정확히 600초**, 전체 RMS **0.056567**, 시작·중간·540초 구간 nonzero를 확인했다. 독립 검사 JSON은 같은 ignored run 폴더에 `independent-timing.json`, `independent-audio.json`으로 보존했다. 오디오 JSON의 MP4 SHA와 별도 `shasum -a 256` 결과가 위 값과 일치하며, timing JSON에는 SHA 필드가 없다. 첫 실패 파일은 위 절에 그대로 보존한다.

독립 리뷰에서 **서로 다른 인접 이미지**만으로는 PTS와 영상 내용의 순서 교체를 검출하지 못한다는 지적을 받았다. 10분 파일을 만든 뒤 `qa/inspect-movie-soak-counter.swift`를 추가해 **각 해독 프레임의 15-bit 시각 카운터를 해당 PTS×30의 예상 번호와 대조**했다. 수정본 MP4는 **18,000개 중 mismatch 0**, 첫 실패 MP4는 존재하는 **17,997개 중 mismatch 0**으로, 전자는 전체 순서가 맞고 후자는 내용 교체가 아닌 누락임을 뒷받침한다. 두 `independent-counter.json`의 SHA도 각각 위 파일 해시와 일치한다. 이 검사를 opt-in 테스트에도 추가했고, **변경 후 2초 실행 60/60·mismatch 0과 관련 테스트 12건 중 11 pass·1 skip·실패0**을 확인했다. 카운터 검사를 포함한 XCTest 자체를 10분 재실행하지는 않았으므로, 10분 합격의 카운터 근거는 같은 MP4의 사후 독립 디코드다.

카운터 판독기는 `xcrun swiftc -parse-as-library qa/inspect-movie-soak-counter.swift -o qa/generated/r80-build231-movie-soak/inspect-movie-soak-counter`로 빌드한 다음 `inspect-movie-soak-counter <soak.mp4>` 형태로 실행한다. 결과는 각 run 폴더의 `independent-counter.json`에 보존했다.

이 검증은 장치 선택 없이 **writer의** 1080p·10분 지속시간·해상도 경계를 통과했다. **0.80 영상 출고 전체를 닫지는 않는다.** 실제 `AlbumCanvasView`의 1080p 캡처와 화면 compositor FPS, output helper가 멈추는 상황, 루프/최소화 상태에서의 실제 앱 10분 파일, 독립 플레이어 감상과 청감 A/V 동기는 최종 빌드 격리 앱에서 별도 확인해야 한다. Scarlett 성공은 합격 조건이 아니다.
