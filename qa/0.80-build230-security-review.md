# 0.80 build230 · trusted AI 파일 작업 보안 검토

범위: `release/0.80.0`의 build230 미커밋 diff. `AgentRunFileGrant`, app-owned ingress, staged `ProjectStore` 게시·폐기, STOP/TTL/replay, 사용자 선택 경로와 응답의 절대 경로 노출을 소스로 검토했다. `/tmp/circlr-build230-integration.log`의 관련 40개 테스트는 실패 0개다. 이 문서는 읽기 전용 코드 검토 결과이며 실제 동시 파일시스템 경합을 재현한 native QA는 아니다.

## 발견 사항

1. **P2 · trusted WAV export가 선택한 물리적 폴더를 유지하지 않음.** `Sources/CirclrApp/AgentWorkspace.swift:531-536`은 시작 시 parent가 디렉터리인지만 확인한다. 이후 `:353-362`의 공용 `writeAgentWAVStage`는 trusted 작업에서도 `createDirectory(..., withIntermediateDirectories: true)`로 parent를 다시 만든다. WAV 렌더 중 사용자가 Finder에서 선택한 폴더를 이동하면 같은 경로에 새 폴더가 생기고, `:653-667`은 그곳에 WAV를 게시할 수 있다. 선택 경로의 symlink가 다른 외부 폴더로 바뀐 경우에도 `Sources/CirclrCore/AgentRunLease.swift:215-219`는 현재 곡 패키지 내부 여부만 다시 검사하므로 다른 물리적 목적지에 쓰일 수 있다. 모델이 경로를 지정하는 취약점은 아니지만 앱 선택 destination capability가 경로 문자열에만 묶여 있다. **수정:** grant 발급 시 parent의 실제 디렉터리 identity를 보존하고 stage 생성·최종 게시를 그 디렉터리에 묶는다. trusted writer는 사라진 폴더를 재생성하지 말고 실패한다. 선택 뒤 parent 이동·symlink 재지정 통합 테스트를 추가한다.

2. **P2 · 취소/게시 실패가 바뀐 stage 디렉터리의 다른 파일을 재귀 삭제할 수 있음.** `Sources/CirclrCore/ProjectStore.swift:393-400`의 `discard`는 stage root의 identity나 내용 재확인 없이 `FileManager.removeItem(at:)`을 호출한다. 게시 경로도 `:418-424`에서 stage fingerprint 불일치를 발견한 뒤 `defer`(`:418`)로 같은 재귀 삭제를 한다. 준비 이후 같은 이름의 stage 디렉터리를 다른 프로세스가 이동시키고 그 자리에 별도 디렉터리를 넣으면, STOP 또는 fingerprint 거절이 그 대체 디렉터리 내용을 지운다. 현재 테스트는 stage media 누락·target 변경만 검사하며 stage root 교체는 검사하지 않는다. **수정:** 폐기는 생성 당시 stage inode와 동일한 디렉터리에만 적용하고, 불일치 시 다른 경로를 삭제하지 않는다. 가능하면 `openat`/`O_NOFOLLOW`와 소유 파일 목록 기반 삭제를 사용한다. stage root 바꿔치기 후 discard/publish가 대체 디렉터리를 보존하는 회귀를 추가한다.

3. **P2 · AI STOP 뒤 큰 저장 stage의 I/O가 계속될 수 있음.** `Sources/CirclrApp/AgentWorkspace.swift:426-434`는 detached `prepareSessionSave`를 cancel하지만 `Sources/CirclrCore/ProjectStore.swift:363-373`의 asset 루프와 `:251-254`의 1 MiB 복사 루프에는 cancellation check가 없다. STOP은 최종 게시를 차단하지만, 큰 미디어를 복사 중인 worker는 끝까지 디스크 공간과 I/O를 사용하고 그때까지 임시 stage가 남을 수 있다. 현재 STOP 통합 테스트는 stage worker 시작 전의 drain을 막아 두는 시나리오만 검증한다. **수정:** 준비 시작·asset별·복사 chunk별 cooperative cancellation을 넣고, 중간 stage 정리까지 확인하는 큰 미디어/느린 복사 회귀를 추가한다. 이것은 STOP 후 게시 권한 우회 발견이 아니라 자원·수명 관리 결함이다.

## 검토에서 확인한 경계와 남은 검증

- grant는 앱 소유 문서와 turn에 묶이고, `save`/`export` 요청의 model `path` 및 unknown/null 필드는 거절된다. 응답은 경로 없는 receipt로 투영하며 실패 문자열도 일반화한다 (`AgentRunLease.swift:291-304,577-600`; `AgentSessionGateway.swift:193-225`). 읽은 코드에서는 trusted 소켓으로 로컬 경로가 직접 반환되는 사례를 찾지 못했다.
- `authorizedOwnedFileJobDestination`은 STOP·TTL·문서 교체·revision을 게시 직전 재검사하고, replay ledger는 ID 재사용을 제어한다. 관련 계약 테스트는 통과했다. 같은 프로세스 MainActor interleave 방지는 외부 파일시스템 변경까지 직렬화하지 않는다.
- 위 1·2번은 파일시스템 상태가 작업 도중 바뀌는 조건부 결함이다. 현재 40개 통합 테스트의 PASS는 그 경합을 커버하지 않으므로 release 보안 gate에서 별도 회귀가 필요하다. 일반 외부 MCP는 원래 별도 raw-path 계약이므로 이 검토의 trusted path-free 판정에 포함하지 않았다.
