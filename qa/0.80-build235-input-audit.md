# 0.80 build235 — 입력 캡처 독립 감사 (2026-09-24)

## 판정

**현재 코드의 10초 시작 timeout은 UI에 실패를 알릴 뿐, HAL 안에서 멈춘 in-process 녹음 worker를 중단하지 못한다.** 이 호스트에서 실제 사용자 입력 PCM을 얻었다는 증거는 없다. 다음 구현 단위는 오디오 입력의 장치 접근·캡처·파일 마무리를 앱 소유 **별도 프로세스**로 옮겨, timeout/STOP 뒤 자식 종료를 확인하고 재시도할 수 있는 계약을 만드는 것이다. 먼저 기본 입력 경로를 이 경계로 옮기고, 선택 UID 경로는 해당 장치의 실제 PCM·종료 검증 전까지 명시적 미지원으로 유지한다. 이 단위 자체를 실제 입력 녹음 성공으로 판정하지 않는다.

## 확인된 현재 상태

- `Sources/CirclrApp/AppStore.swift:1173-1200`의 사용자 오디오 녹음은 권한을 요청하고 `AudioRecorder.start(...)`를 호출하지만 `selection`을 전달하지 않는다. 따라서 기본값 `.systemDefault`만 사용한다. `AudioRecorder.swift:65-71`은 기본값을 `EngineCaptureBackend`의 `AVAudioEngine.inputNode`로 열고, 명시적 UID는 장치를 재검증한 후 `selectedCaptureUnavailable`로 종료한다. `InputDeviceBinding.swift`의 AUHAL 바인딩은 제품 캡처 backend에 연결되지 않았다. 선택 장치용 제품 UI/PCM 경로가 있다는 뜻으로 해석하면 안 된다.
- `AudioRecorder.swift:34-44`에서 `backend.start`와 `backend.stop`은 한 serial queue를 사용한다. `start`가 HAL 동기 호출에서 반환되지 않으면 그 뒤에 제출한 `finish`는 실행될 수 없다. `AudioRecorder.swift:83-109`의 timeout은 `CaptureControl`을 disable하고 시작 completion에 실패를 돌려주지만 `attempt`는 `finish`의 reply가 올 때만 지운다. 따라서 blocked `start`가 무기한이면 phase는 `cancelling`, `busy=true`이고 `start`의 재시도 guard(`:77`)가 계속 실패한다. `deinit`의 `finish`(`:74`)도 같은 queue에 쌓인다. `stop`의 `engine.stop`, callback drain 및 `TakeWriter.finish`(`:164-173`) 역시 동기 완료를 기다리므로 종료 시점에도 같은 종류의 지연이 가능하다. 이는 코드 경로로 확인된 위험이며, 이 Mac에서 **제품의** `AVAudioEngine.inputNode`가 실제로 영구 대기했다는 관찰은 아니다.
- 기존 `Tests/CirclrAudioTests/AudioRecorderTests.swift:44-60`의 지연/timeout 테스트는 `DispatchSemaphore`로 시작을 늦춘 뒤 명시적으로 `signal()`하여 cleanup이 끝나는 경우를 검증한다. gate를 풀지 않는 경우의 bounded cleanup·재시도는 검증하지 않는다. `InputDeviceRecorderTests.swift:83-100`은 선택 입력이 fail-closed인 점만 검증한다. `CaptureControl.swift:15-25`는 callback 수집을 닫지만 HAL 동기 호출을 취소하지 않는다.
- [선택 입력 조사](0.80-selected-input-investigation.md)의 독립 **외부 프로세스** spike에서는 CalDigit을 명시한 `AVCaptureSession.startRunning()`과 `AudioDeviceCreateIOProcID`가 각각 10초 동안 반환되지 않았다. 감독 프로세스가 자식을 종료했고 callback/PCM은 확인되지 않았다. 이 spike는 제품 `AudioRecorder` 실행이 아니며 원인을 Scarlett·CalDigit·TCC·HAL 중 하나로 특정하지 않는다.
- 이번 read-only `system_profiler SPAudioDataType`은 정상 종료했다. 현재 입력 장치는 `CalDigit Thunderbolt 3 Audio`(2채널)와 `Scarlett 6i6 USB`(6채널)로 보이고 기본 입력은 Scarlett이다. `Mac Studio 스피커`는 출력 장치다. 장치가 목록에 보인다는 사실은 캡처 가능한 PCM이나 오디오 품질의 증거가 아니다. 시스템 기본 장치·권한·사용자 프로젝트는 변경하지 않았다.
- `Resources/Info.plist:44-45`에는 메인 앱의 `NSMicrophoneUsageDescription`이 있다. 새 자식 실행 파일의 마이크 TCC 귀속·서명·권한 동작은 아직 검증되지 않았으므로 앱에서 권한을 얻은 것만으로 자식의 접근 성공을 가정하지 않는다. 현재 `scripts/package-app.py`는 별도 오디오 출력 helper를 각각 서명·검증하는 방식이다.

## 다음 구현 단위: 입력 worker의 격리·회복 계약

1. `Tools/CirclrInputWorker/main.swift`와 `Sources/CirclrAudio/InputWorkerService.swift`를 추가하고 `Package.swift`, `scripts/build-app.sh`, `scripts/package-app.py`에서 **앱에 포함된 서명된 실행 파일만** 시작하도록 한다. 기본 입력의 `AVAudioEngine` 생성, `inputNode`, tap, `TakeWriter`, stop/finish는 모두 자식에서 수행한다. 앱의 **입력 캡처 경로**는 HAL API를 직접 호출하지 않는다. 제품에서 아직 쓰지 않는 `InputDeviceCatalog.available()`도 UI에 직결하지 않는다. 기존 `InputDeviceBinding`의 선택 UID는 검증될 때까지 fail-closed로 둔다.
2. 요청은 일회성 session ID, `systemDefault` 또는 명시적 UID, 최대 녹음 frame/시간, 앱이 소유한 제한된 take 임시 경로만 허용한다. 응답은 `starting`/`recording`/`stopping`/`finished`/`failed`, 요청·장치 재검증 결과, sample rate/channels, 증가하는 frame count/peak, 최종 파일의 frame count를 담는다. 기본 입력의 조회 ID만으로 실제 신호 출처를 확정했다고 표시하지 않는다. 모든 frame·형식은 범위를 검증하고 IPC 길이·응답 수·대기 시간을 제한한다. 선택 UID가 다른 장치로 바뀌거나 사라지면 실패하며 기본 입력으로 조용히 대체하지 않는다. UID·사용자 경로는 일반 로그에 출력하지 않는다.
3. 시작 deadline(현재 10초), STOP/finish deadline, helper 종료 grace를 각각 구분한다. deadline 또는 사용자 STOP 뒤 자식에 종료 요청 → 짧은 grace → 필요하면 SIGKILL을 보내고, **자식 PID가 실제 종료·reap된 뒤에만** 다음 캡처를 허용한다. HAL이 계속 block되어 PID 종료를 확인할 수 없는 예외에서는 UI는 계속 사용할 수 있게 하되 입력 재시도는 닫고 오류를 표시한다. `waitUntilExit`만 별도 deadline 없이 MainActor에서 호출해서는 안 된다. 부모의 `attempt`는 자식 종료·파일 판정 뒤 단 한 번만 해제하고, 늦은 frame/완료 메시지와 이전 session ID는 무시한다.
4. 앱은 자식의 `finished` 메시지만으로 take를 만들지 않는다. 자식 종료 후 제한된 임시 CAF를 다시 열어 frame count/format과 실제 파일을 확인한다. 성공한 file만 기존 `AudioTakeEditing.save` 대상 스냅샷에 적용하고 Undo를 유지한다. crash/timeout/쓰기 오류의 부분 파일은 원래 프로젝트에 붙이지 않고 안전한 recovery 위치에 보존하거나 명확히 폐기한다. 복구 파일에는 정상 take라는 표시를 하지 않는다. 실제 소리 유무는 frame 수와 다르므로 별도 PCM 검사가 필요하다.

## 검증 계약

- **RED→GREEN 자동 테스트:** 자식이 `start`/`stop` 전 영구 대기하는 fixture, 시작 직후 crash, 늦은 성공, STOP 중 응답, 잘못된 session ID, 잘못된 형식/길이/경로, 0-frame, 과도한 frame count, 중복 시작을 각각 넣는다. timeout 뒤 UI completion 1회, 수집 중단, 자식 종료 확인, 재시도 성공, 파일 보존/미삽입을 검증한다. HAL fixture를 앱 프로세스의 멈춘 thread로 만들지 않는다. 실제 자식 PID를 관찰하는 process-level 테스트가 필요하다.
- **실기기 acceptance:** 별도 안정적인 입력 장치가 있는 격리된 macOS 호스트에서 서명된 최종 앱과 helper의 권한을 확인한다. 기본 입력과 명시적 UID를 각각 녹음해 callback의 연속 frame, 1/2채널 형식, 재열기 가능한 CAF, 입력 신호가 있는 구간의 nonzero PCM, STOP·재시도·분리·문서 변경 후 자식 정리를 확인한다. 시스템 기본 장치는 바꾸지 않고 선택 UID가 오인 바인딩되지 않았음을 확인한다. 실제 물리 청취/녹음은 별도 사용자 확인으로 남긴다.
- 이 호스트의 Scarlett/CalDigit이 계속 HAL에서 멈추면 process test의 timeout·복구만 PASS로 기록한다. **사용자 입력 녹음 PASS, 선택 입력 PASS, 발매 가능 DAW 판정은 불가**하다. 다른 장치/호스트의 실제 PCM과 최종 앱 권한 증거가 들어와야 그 gate를 연다.
