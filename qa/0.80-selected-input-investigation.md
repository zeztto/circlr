# 0.80 선택 입력 장치 native 조사 (2026-09-24)

## 판정

**현재 호스트에서 선택 장치 독립 캡처는 미검증이며 제품 통합 보류.** `CalDigit Thunderbolt 3 Audio`를 명시적으로 선택한 두 별도 경로 모두 10초 제한에서 멈췄다. `AVCaptureSession`은 `startRunning()`에 진입한 뒤 반환되지 않았고, 직접 Core Audio 경로는 `AudioDeviceCreateIOProcID` 호출에서 반환되지 않았다. 어느 경로에서도 callback, 실제 PCM frame, nonzero sample을 얻지 못했다. 이 결과는 선택 장치 경로가 원리적으로 불가능하다는 증거가 아니며 이 호스트의 장치/driver/HAL 상태에서 성공을 주장할 수 없다는 범위로 제한한다.

## 조사 범위와 현재 코드

- Native spike는 기존 기본 checkout의 `d88ea5d`에서 독립 실행 파일로 수행했으며, 결과·재현물을 `release/0.80.0` 작업 트리로 옮겨 기록했다. 이 spike는 제품 녹음 backend 자체를 실행한 검사가 아니다.
- `release/0.80.0`의 `AudioRecorder`는 기본 입력에서 `EngineCaptureBackend`를 사용한다. 이 backend는 `AVAudioEngine.inputNode`를 사용하므로 앱의 특정 입력 UID를 바인딩하지 않는다([Apple: AVAudioEngine.inputNode](https://developer.apple.com/documentation/avfaudio/avaudioengine/inputnode)). 선택 UID에는 별도 `SelectedCaptureBackend`가 있으나, 장치의 존재·활성·입력 채널·UID를 재검증한 다음 명시적 `selectedCaptureUnavailable` 오류로 종료한다. 실제 선택 장치 PCM 경로는 현재 제품에 없다.
- `Sources/CirclrAudio/InputDeviceBinding.swift`에는 AUHAL 장치 바인딩·재검증 계약과 장치 catalog가 있다. 이전 AUHAL 실기기 spike는 `AudioComponentInstanceNew`에서 지연됐다. 이번 독립 AVCapture/IOProc spike도 다음 단계에서 지연되어, 이 host에서 해당 결합을 제품에 연결할 성공 근거가 없다. recorder의 10초 시작 timeout이 HAL 내부 동기 호출을 실제로 중단·정리하는지는 별도 검증이 필요하다.

## 격리 검증

환경: macOS 26.5.1 (arm64), Apple Swift 6.3.3. `system_profiler SPAudioDataType`에서 입력은 Scarlett 6i6 USB와 CalDigit Thunderbolt 3 Audio(2채널)이며 Mac Studio 내장 입력은 표시되지 않았다. Scarlett이 기본 입력·출력·시스템 출력이었다. 이 조사에서는 CalDigit을 비 Scarlett 기준 장치로 선택했다. `AVCaptureDevice.authorizationStatus(for: .audio)`는 `.authorized`였다. 장치 UID/serial은 출력 또는 추적 문서에 기록하지 않았다.

| 경로 | 명시적 선택 / 성공한 단계 | 마지막 반환되지 않은 호출 | 제한 결과 |
| --- | --- | --- | --- |
| `AVCaptureDeviceInput` + `AVCaptureAudioDataOutput` | DiscoverySession에서 CalDigit 선택 → `AVCaptureDeviceInput(device:)` → input/output session 구성 | `AVCaptureSession.startRunning()` | 10초 후 감독 프로세스 종료. callback/PCM summary 단계에 도달하지 못함. |
| `AudioDevice` IOProc (AudioComponent 미사용) | CalDigit `AudioDeviceID` 선택 → input 2채널 확인 → nominal 48,000 Hz → input virtual format 48,000 Hz, 2채널, `lpcm`, 32-bit Float, packed | `AudioDeviceCreateIOProcID` | 10초 후 감독 프로세스 종료. IOProc 등록 완료/시작/callback 관찰 없음. |

두 결과의 원본 stage log와 재현 소스는 gitignore 대상인 `qa/generated/r80-selected-input-spike/`에 있다. `AVCapture` 경로에서는 `startRunning()`이 반환되지 않아 종료/summary를 출력하지 못했으므로 delegate 호출 여부 자체를 확정하지 않는다. Core Audio의 형식은 장치 속성 조회값이며 **실제 캡처된 PCM의 검증값이 아니다**. `formatFlags=9`는 float + packed이고 noninterleaved bit가 없다는 장치 format 해석이다.

외부 `run-spike.py`가 각 실행 파일을 10초로 제한하고 초과 시 해당 프로세스를 종료했다. 실행 후 두 spike 프로세스가 남아 있지 않음을 `pgrep`로 확인했다. 사후 `system_profiler`는 Scarlett을 여전히 기본 입력·출력·시스템 출력으로 표시했다. 실행 파일 어디에도 시스템 기본 장치를 바꾸는 property setter, 사용자 project 쓰기, 오디오 파일 쓰기는 없다.

재현:

```sh
swiftc qa/generated/r80-selected-input-spike/avcapture-selected-input.swift -o qa/generated/r80-selected-input-spike/avcapture-selected-input
clang -std=c11 -O2 qa/generated/r80-selected-input-spike/audiodevice-selected-input.c -framework CoreAudio -framework CoreFoundation -o qa/generated/r80-selected-input-spike/audiodevice-selected-input
python3 qa/generated/r80-selected-input-spike/run-spike.py avcapture-selected-input
python3 qa/generated/r80-selected-input-spike/run-spike.py audiodevice-selected-input
```

## API 근거와 다음 계약

- Apple은 `AVCaptureDevice.DiscoverySession`으로 장치를 찾아 선택하고, `AVCaptureDeviceInput(device:)`로 그 **특정 장치**를 session 입력으로 연결하도록 정의한다([DiscoverySession](https://developer.apple.com/documentation/avfoundation/avcapturedevice/discoverysession), [device input initializer](https://developer.apple.com/documentation/avfoundation/avcapturedeviceinput/init%28device%3A%29)). `AVCaptureAudioDataOutput` delegate는 serial queue에서 sample buffer를 제공한다([Apple: setSampleBufferDelegate](https://developer.apple.com/documentation/avfoundation/avcaptureaudiodataoutput/setsamplebufferdelegate%28_%3Aqueue%3A%29)). 그러나 Apple은 `startRunning()`이 blocking call이라고 명시한다([Apple: AVCaptureSession](https://developer.apple.com/documentation/avfoundation/avcapturesession)); 이 호스트에서는 명시적 장치 바인딩 뒤에도 그 지점에서 정지했다.
- Core Audio의 `AudioDeviceCreateIOProcID`는 지정한 `AudioDevice`에 callback을 등록하고 `AudioDeviceStart`가 해당 proc의 I/O를 시작한다([create](https://developer.apple.com/documentation/coreaudio/audiodevicecreateioprocid%28_%3A_%3A_%3A_%3A%29), [start](https://developer.apple.com/documentation/coreaudio/audiodevicestart%28_%3A_%3A%29), [IOProc input data](https://developer.apple.com/documentation/coreaudio/audiodeviceioproc)). 이 경로는 `AudioComponentInstanceNew` 자체를 호출하지 않지만 이 호스트에서는 proc 등록이 정지했다. 이 지점까지의 관찰로 원인을 Scarlett, CalDigit, TCC, 또는 HAL 중 하나로 확정할 수 없다.
- 다음 native gate는 **응답하는 별도 입력 하드웨어가 있는 격리 호스트**에서, 선택 UID를 당시 `AudioDeviceID`/`AVCaptureDevice`로 재해석하고 동일한 제한 실행을 반복하는 것이다. 선택 장치가 사라지면 실패해야 하며 시스템 기본 입력으로 조용히 fallback해서는 안 된다. callback에서 source format, 연속 frame 수, nonzero PCM 및 종료 후 리소스 해제를 확인한 뒤에만 제품 backend를 선택한다. 실제 app 권한은 앱 bundle의 `NSMicrophoneUsageDescription`과 entitlement를 확인해야 한다([Apple: capture authorization](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)); CLI의 `.authorized` 결과를 앱 권한 증거로 대체할 수 없다.
- 통합 시 `AudioRecorder`의 backend factory가 선택 장치의 안정적 식별자를 받도록 하고, 장치 선택 → 권한 → backend 구성 → 실제 callback/format 확인 → `TakeWriter` 시작 순서를 지킨다. in-process serial queue만으로 HAL blocking call을 중단할 수 없다는 현재 실패 양상을 반영해 종료/재시도 계약을 별도 프로세스 경계 또는 재현 가능한 bounded cleanup으로 검증해야 한다. 이 단계는 제안이며 제품에 구현하지 않았다.
