# 0.20 · 녹음 lifecycle 검증 중

2026-09-08, macOS 26.5.1 / Apple Silicon. 현재 사용 앱은 **0.19.0**이며 0.20.0 build 22는 소스와 전용 검증 앱 단계다. 작은 창의 대기 상태 버튼·단축키 안내·트랙 이동 가독성·재열기를 확인했다. 실제 입력 녹음과 녹음 중 UI·종료 복구 검증이 남아 0.20 앱 교체·설치 키트 갱신·출고를 보류한다.

사용자의 한도 해제 안내 후 독립 녹음 엔진 리뷰를 dispatch했지만 `agent thread limit reached`로 거부됐다. development-lead → 구현 → 읽기 전용 코드/보안 검토 → QA를 같은 에이전트가 순차 수행했다. 독립 리뷰나 병렬 실행이 성공한 것으로 계산하지 않는다.

## 완료한 검사

- `.build/recording-quality`의 전체 오프라인 Swift **160개 통과**. 실제 장치 출력에 의존하는 `testArrangementRenderExportAndPlayback` 한 개는 제외했다. 이후 새 녹음 왕복 통합 검사 **1개를 별도 실행해 통과**했다. 총 161개의 서로 다른 검사이며, 161개 전체를 한 번에 재실행한 기록은 아니다.
- Python MCP **14개**, 음악 agent kit **9개** 통과. 새로운 `circlr_record`를 포함한 15개 도구의 schema와 읽기 전용 역할의 모든 변경 명령 거부를 검사했다.
- `.build/recording-release` 녹음 로직의 release 빌드는 25.02초, 이후 이동 메뉴 대비·선택 접근성 수정의 release 빌드는 19.56초에 warning 없이 완료됐다. 현재 소스/QA 실행 파일 UUID는 `889E481F-C710-30DC-BF59-E18C16025DB8`이다. 이전 녹음 로직 검증 binary `C98ADBF2-69FF-3540-8CA6-F56703199A91`은 보관했다. 두 빌드 사이 녹음 엔진·Core·MCP 로직은 동일하다.
- 느린 시작 → 즉시 gate 차단 → 늦은 응답 정리 → 재시도, 시작 실패/timeout/중복 시작, 느린 종료, 종료 실패, 입력 변경, recorder 해제를 주입된 backend로 확인했다. 실제 드라이버를 시작한 결과는 아니다.
- 실제 CAF readback으로 6채널 callback 중 첫 두 채널, 12,000 frame block의 분할, 10,000 frame cap과 peak를 검사했다. write queue가 밀리면 원본 경로를 포함한 오류를 반환하는 기존 경계를 유지한다.
- `AudioTakeEditing`은 원래 project/arrangement/use/track/lane 검증과 테이크 생성·활성화를 한 candidate에 적용한다. 기존 MIDI, 이전 오디오 take, 다른 use와 JSON 왕복을 검사했다. 잘못된 대상과 invalid duration은 project를 바꾸지 않는다. 앱은 이를 한 `mutate`/Undo로 감싸지만 실제 GUI Undo는 아직 대기 중이다.
- `RecordingRoundTripTests`는 제어된 **96,000 stereo frames / 48 kHz / 2초**를 callback 경로에 넣었다. CAF readback, take의 실제 렌더, `.circlr` 저장·재열기 후 렌더가 양 채널 원본 PCM과 정확히 같았다. 원래 CAF를 테스트 임시 폴더에서 지운 뒤에도 embedded media로 렌더됐다. 바운스는 24-bit **1 LSB 이하**, 바운스 복원은 PCM 동일이다. 이는 합성 검사용 데이터이며 실제 마이크·청취 평가 또는 제품 데모 음악이 아니다.

## 실제 앱에서 확인한 범위

전용 `com.circlr.hierarchyqa` 0.20.0 build 22가 실행됐다. 별도 socket의 snapshot과 AX에서 새 상태를 확인했다. 다른 앱과 기본 오디오 장치·OS 설정은 변경하지 않았다.

앱이 잘못된 projectID, 현재와 다른 revision, 선택 대상이 없는 `record` 요청을 모두 거부했다. 녹음 상태·project/revision·기존 open job은 요청 전후 동일했다. 마이크 권한 요청이나 입력 수집은 시작하지 않았다. 응답은 관찰된 세 요청에서 각각 0.6 / 21.1 / 12.0 ms였으며 일반적인 성능 보장으로 사용하지 않는다.

초기 `recording-QA.circlr` 열기 job은 macOS 문서 폴더 접근 승인을 기다렸다. 시스템 로그에서 새 ad-hoc 서명과 이전 code requirement가 일치하지 않아 `kTCCServiceSystemPolicyDocumentsFolder`를 다시 요청한 것을 확인했다. worker sample은 manifest 읽기 대기였고 MainActor/MCP는 응답했다. 관찰 도우미의 timeout 이후에도 같은 job을 유지했고 13:27에 **완료**됐다. OS 요청이나 설정은 대신 조작하지 않았다. 이후 대비 수정 빌드는 같은 QA 사본을 다시 열어 완료됐으며, 녹음은 시작하지 않았다.

canvas 1080×747에서 콘솔을 연 채 오디오 녹음 버튼·⌥⌘R 도움말과 실제 메뉴·키보드 안내를 확인했다. 실제 녹음 단축키 실행은 허용 대기 중이다. 선택한 오디오 이동 메뉴는 macOS가 label의 민트 배경을 표시하지 않아 어두운 글자가 묻혔다. 선택 글자를 민트색으로 바꾸고 `.isSelected` 접근성 상태를 추가했다. 수정 전후 화면에서 가독성을 확인했고, 단일 MIDI 이동 버튼의 AX selected 상태도 확인했다. GUI에서 MIDI → 오디오 메뉴 → 원래 조각으로 복귀한 뒤 graph/lane/revision 113이 동일했다.

사용자에게 별도로 요청한 실제 입력 검증 범위는 최대 두 번, 각 2초 이하다. 허용 답변 전에는 실행하지 않는다. 허용되더라도 macOS Microphone 접근 요청은 사용자가 선택해야 한다.

## 검토 결과와 남은 조건

새 recorder의 engine/input/tap/start/stop과 파일 마무리는 serial worker에 속한다. callback 상태는 C atomic에 두며 gate를 먼저 닫고 진행 중 callback 뒤에 파일을 drain한다. timeout은 수집 차단이며 OS driver 호출의 강제 취소가 아니다. driver가 응답할 때까지 재시작을 막고 종료 요청은 최대 10초 후 앱 종료를 취소한다.

MCP record는 project/revision 검증 후에만 시작한다. 파일 경로 인자를 받지 않으며 앱이 로컬 takes 폴더의 새 UUID 경로를 결정한다. 이전 권한 응답은 현재 요청 ID와 project/revision/선택을 다시 확인한다. 결과를 원래 대상에 넣지 못하면 파일을 보존하고 Finder 경로를 제공한다. 새 shell/network 실행이나 credential 처리 경로는 없다. 검토한 범위에서 남은 high/critical 결함을 찾지 못했으며 하드웨어 호환성 승인으로 간주하지 않는다.

남은 native acceptance:

1. 완료: 정확한 QA 사본과 선택 대상 확인, 120 BPM/4박/1회로 2초 cap 설정·저장. native timeline의 duration=2도 확인했다.
2. 부분 완료: 콘솔을 연 작은 창의 직접 녹음 버튼·메뉴·⌥⌘R 안내와 이동 가독성 확인. 실제 녹음/취소/마무리·입력 시간/레벨/채널 표시는 허용된 입력 검증 때 확인한다.
3. 허용된 실제 입력 → CAF frame/rate/channel 확인 → 테이크 → 편집/바운스 → 한 번의 Undo → 저장/재열기. 무음이어도 파일 검증과 음악 품질 평가를 구분한다.
4. 실패/정리 상태의 경로 복구와 종료 동작 확인 후 README/CHANGELOG를 출고 상태로 변경하고 package/kit/서명·UUID·private remote를 검증한다.

입력 장치/채널 선택, 반주 transport 동기와 latency 보정, 연속 실시간 그래프/PDC, Scarlett 출력 및 실제 MP4 녹화는 후속 범위다. 전체 개발 목표는 유지한다.

검증된 구현은 private `codex/recording-lifecycle` source checkpoint로 보관한다. native 입력 acceptance를 건너뛰어 main이나 사용 앱을 교체하는 출고는 아니다. 포트 기반은 별도 `codex/eight-direction-ports` 브랜치에서 진행하며 두 구현을 통합한 테스트 결과로 합산하지 않는다.
